# Kimi 单票探测分析（2026-09-07，对照源码 v0.3.3 @ 9027d8f，pi-subagents 0.65.1）

本文回答 `run-2026-09-07.md` 第 9 节的问题，并对照 `.scratch/planner-only-cost-control/spec.md` 评估覆盖面。所有结论都在本分支材料 + 源码里可复核。

## 0. 一句话结论

这次 25 分钟、约 $1.23（不含 Root k3 真钱）的失败运行，**主因是三个编排正确性 bug，不是缺少费用策略**。费用控制规格（cost-control spec）方向正确，但它假设「流水线本身是对的，只是没上限」；本次探测说明前提不成立，规格里没有任何一条能修复这三个 bug。建议先修 bug，再按规格分阶段实施。

## 1. 发现的问题（按造成的损失排序）

### P1. 同步 Oracle 结果被插件误判为「异步启动回执」（插件 bug，确认）

证据（Root 会话 JSONL，tool_result 的 details）：

| Oracle | Root 传入 | 返回时刻 | details.runId | details.asyncId | durationMs | 插件回复 |
|---|---|---|---|---|---|---|
| 1 `79ce6075` | `async:false` | 00:07:35 | 有 | **无** | 30 130 | Async delegation has started |
| 2 `ab785e71` | `async:false` | 00:08:51 | 有 | **无** | 48 250 | 同上 |
| 3 `29c1c567` | `async:false, context:fresh` | 00:10:00 | 有 | **无** | 48 887 | 同上 |
| 4 `f3ad9f6c` | 省略 async | 00:10:53（0.06 s） | 有 | **有** | — | 同上（这次是真异步） |

前三次都是**前台同步完成**的：父进程阻塞了 30–49 s，返回时子进程已经写完 meta/output（run 报告里「status 看不到 run」正是因为 run 早已结束）。不是 pi-subagents 把 `async=false` 改掉了。

根因在 `orchestrate.ts` 的 `isAsyncLaunchReceipt()`（约 332–354 行）：

1. `looksLikeWorkerReport(text)` 为假（Oracle 输出是 markdown 散文）→ 不能短路。
2. details 没有 `asyncId`，`asyncRequested` 为假 → 继续。
3. JSON.parse 失败 → 走「散文标记」启发式，四个正则命中 ≥2 即判为异步回执。
4. pi-subagents 0.65.1 的**前台**结果文本恰好同时带两条：`runs/foreground/subagent-executor.ts:677` 在首行前缀 `Run fan-out: 1/64 used…`，`missions/lifecycle.ts:244` 在末尾追加 `Mission: <id> (completed)`。两条标记都命中 → 误判。

Worker-1/2 没中招只是因为它们的输出是 WorkerReport JSON，被第一步短路。**任何返回散文的前台角色（Validator、Explorer）都会稳定触发这个 bug。**

连带问题：插件回复的「Async delegation … has started」**不带 runId**，Root 只能无 id 地 `bg_wait`，而 pi-subagents 的无 id `bg_wait` 在启动后几秒内报「No active async runs」（第四次 00:10:53 启动、00:10:58 仍报空，00:11:03 status 才看到）。Root 在 print 模式下没有其它办法拿到 id。

损失：三次 Oracle 白跑（$0.046）、Root 自己补核验、约 5 分钟墙钟；这是 review 之前多花时间的全部来源。

修法：

- 判定顺序改为：details 有 `asyncId` → 异步回执；否则 details 有 `runId` 且 `results[0].outputState/exitCode` 存在（或 `mission.status === "completed"`）→ 已完成的前台结果；`asyncRequested === false` 时**禁止**走散文启发式。
- 散文启发式只保留 `detached and running in the background` 这类唯一语义的标记；`Mission:` 和 `Run fan-out:` 在前台完成结果里同样出现，必须从标记列表删掉。
- 异步回执文案带上 runId，并明确写 `bg_wait id=<runId>`。
- 回归测试：用 0.65.1 真实前台结果文本（含 `Run fan-out:` 首行和 `Mission: … (completed)` 尾行）跑 Oracle/Explorer 两种 kind，断言走完成路径。

### P2. 异步 Reviewer 的完成通知被当成 WorkerReport 解析（插件 bug，确认）

`orchestrate.ts` 的 `handleAsyncNotify()`（约 1222–1252 行）只分流了 `validator`，`reviewer` 直接落到 `handleWorkerResult()`，于是 00:13:03 出现「Worker output … is not a valid WorkerReport / status must be …」。同步路径（约 1216 行）是分流正确的。

后果：ReviewResult 没有经过 `handleReviewerResult` 的身份/版本绑定检查，也没有推进 review 状态机；Root 只是从 notify 原文里读到 `request_changes` 然后自行开纠偏 Worker。因为 pi-subagents 是 asyncByDefault，Root 只要省略 `async` 字段，Reviewer 就一定走这条坏路径。

修法：在 `handleAsyncNotify` 补 `reviewer` 分支；测试覆盖「异步 Reviewer 通知 → ReviewResult 被记录、round 递增」。

### P3. Root 嵌入的 TaskSpec 被静默丢弃（Root 用法错 + 插件失败模式太安静）

Root 写的是 `{"taskId":"oracle-status-line-01","title":…,"scope":…,"acceptanceCriteria":…}`，没有 `objective` 字段。`task.ts` 的 `extractTaskSpec()` 要求顶层有 `objective`，于是插件在 `orchestrate.ts:641` 创建了占位 Task `(unspecified — parent did not embed a TaskSpec)`，canonical id 为 `T-20260907-001`。

连锁反应：

- Worker-1 按 Root 给的 id 回报 → 身份检查拒绝 → 多一轮报告修正（Worker-2，$0.01、25 s，且吃掉一个 review round）。
- Reviewer packet 的 `objective` 为空、`acceptanceCriteria` 为空，Reviewer 只能对着 Worker 自述审。
- `packetSpec.budget` 不存在 → 任何 usageBudget 都没有下传（见 P5）。
- `validation.required` 未知。

修法：

- 插件侧：JSON 候选里有 `taskId`/`acceptanceCriteria`/`scope` 但缺 `objective` 时，返回**明确 warning**（「embedded spec ignored: objective missing」）而不是静默占位；可考虑接受 `title` 作为 `objective` 别名。
- 文档/Root prompt 侧：给出最小合法 TaskSpec 样例，说明 taskId 由插件分配、Root 不要自造。
- 这一点对 cost-control spec 尤其关键：规格的预算、验证要求都挂在 TaskSpec 上，TaskSpec 静默失效等于整套机制被绕过。

### P4. Worker `npm install` 弄脏 lockfile → evidence stale → request_changes（Worker 合同缺一条）

Worker-1 为了跑测试先 `npm install`，lockfile 从 0.3.2 同步到 0.3.3，但只提交了两个源文件。插件的新鲜度检查和 Reviewer 都正确地拒绝了「报告之后 in-scope 路径仍在变」——这是机制在正常工作，不该放松。问题是合同没有禁止副作用。

修法：`wrapWorkerContract()` 加一条「不要运行 `npm install`/修改 lockfile，除非票明确要求；需要装依赖用 `npm ci` 并把 lockfile 写进 changedFiles」。同时 Root 纠偏时优先 `revert`，不要再让 Worker 自己判断。

### P5. 纠偏 Worker 死循环，210 轮、约 $0.98，没有任何护栏触发

Worker-3 第一步 `git checkout -- package-lock.json`（此时树已干净，空操作），之后同一条 `node --experimental-strip-types index.test.mjs` 跑了 207 次直到被人工杀掉。transcript 里 **0 条** long-running/budget 通知。

原因叠加：

- 没有 TaskSpec（P3）→ `roles.ts:140` 的 usageBudget 下传条件不成立。
- 插件没有给纠偏/报告修正类委派设默认上限；pi-subagents 支持 `toolBudget`（硬性工具调用上限）和 `usageBudget`，插件一个都没用。
- 模型是 `kimi-for-coding:off`（见 P6），推理关闭的便宜模型在「测试已通过但树不变」的状态下判断不了「该停了」。

修法：

- 纠偏、报告修正、Validator 委派给**默认** `toolBudget.hard`（例如 20）和 `usageBudget.costUsd.hard`，不依赖 TaskSpec 是否写了 budget；TaskSpec 有 budget 时取更严者。
- 这是 cost-control spec 的「累计预算」范畴，但规格明确说未配置预算的 Task 保持可运行、不设上限；本次说明**每次委派的默认地板**必须存在，否则一次纠偏就能烧掉整张票预算的 5 倍。

### P6. Worker/Oracle 的 thinking 没有生效（`:off`），只有 fresh 上下文的孩子拿到了 override

settings 的 `subagents.agentOverrides` 给 worker=high、oracle=medium、reviewer=high。实际：

| 委派 | context | 实际 thinking |
|---|---|---|
| Worker-1/2/3 | fork（默认） | off |
| Oracle-1/2/4 | fork | off |
| Oracle-3 | **fresh** | **medium** ✓ |
| Reviewer | fresh（插件强制） | **high** ✓ |

4/4 与「fresh 才应用 override，fork 落到 `off`」一致。pi-subagents 侧 `child-session.ts:220-229` 在 fresh 路径把 `launch.model` 连同 thinkingLevel 解析进新会话；`prompt-audit.ts:95` 有 `ctxThinking ?? "off"` 的回退。fork 路径具体在哪丢的没有逐行追，但插件侧不需要等宿主修：

修法：Worker 和 Validator 默认 `context: "fresh"`（cost-control spec 已提出 Worker fresh，这里再加一个理由，并把 Validator 一并纳入）。同时在 usage 记录里把 `requested thinking` 与 meta 里的实际 `model:thinking` 对比，不一致就在状态里显示。

### P7. Root k3-256k 不在 pricing.json，Root 费用显示为未知

`~/.pi/agent/planner-only/pricing.json` 是用户机器上的文件（README:215），没有 k3 费率 → `costUnknown: true`、`root.costUsd` 缺失。本次 Root 35 轮 / 93 万 cacheRead 的真钱只在供应商账单上。spec 已经覆盖「未知不等于零」的展示要求；实操上还应在插件启动或 `/planner-only status` 时警告「Root 模型无费率」。

### P8. 小问题

- Bounded oracle 合同说「read/grep 确认测试存在」，Root 的任务文本却明确要求「跑 named test suite」，四次 Oracle 都跑了。合同是前缀、任务是正文，模型听正文。要么合同允许 named test（更合理），要么把冲突指令过滤掉。
- `lastWorkerValidationPassed()` 在没有报告时返回 true → bounded 模式。spec 的 Problem Statement 已指出，与源码一致。

## 4. 是否认可该规格

**方向认可，顺序和范围有保留。**

认可的部分：

- 角色模型策略显式化、拒绝静默回退；Worker 默认 fresh 且只传有界执行包；验证状态五分法、空结果不算通过；预算按 Task 累计、重试不重置；upper bound 改口为换价估算；费用对照实验规范；不在宿主没有能力时声称硬上限。这些都是对的，且与 v0.3.3 源码现状描述一致（我逐条核了 `roles.ts`、`orchestrate.ts`、`usage.ts` 对应位置）。
- 测试接缝坚持公开生命周期和真实 pi-subagents 契约，不加测试专用接口——本次 P1 恰恰是一个只有真实宿主输出文本才能暴露的 bug，证明这个原则值得坚持。

保留意见：

1. **前提不成立时规格无法生效。** 规格假设流水线正确、只差限额；本次表明单票最常见的失败是编排 bug。若按规格现有顺序（验证可信性 → 模型策略 → 上下文隔离 → 累计预算）先干，P1/P2/P3 依然会让每次真实运行失败，也就永远跑不出规格第 91 条要求的费用对照样本。
2. **范围偏大。** 累计预算 + 原子预留 + 并发账本 + 幂等结算 + 恢复重放，是一整套小型计费系统。在一次单票跑不完的现状下，这部分的边际收益低于一个 20 行的 `toolBudget` 默认值。
3. **缺三条应补入的行为约束：** TaskSpec 失效必须显式失败；每次委派必须有默认 tool/usage 地板（与 Task 累计预算取严）；模型策略把 thinking 纳入 requested/actual 对比，Validator 与 Worker 同样默认 fresh。
4. **建议的实施分期：**
   - A（先做，全部是小改 + 回归测试）：P1 回执判定重写 + 回执带 runId；P2 reviewer 分支；P3 TaskSpec 显式失败；Worker/Validator 默认 fresh；纠偏/报告修正默认 `toolBudget`；Worker 合同禁 `npm install`；Root 模型无费率时警告。做完后**重跑同一张票**，目标是一次 PASS、约 5 分钟、孩子约 $0.19。
   - B：规格里的角色模型策略（含 thinking）+ 诚实展示。
   - C：规格里的验证五分法与 Validator 补检。
   - D：累计预算与预留（此时才有稳定跑完的样本来校准限额）。
   - E：费用对照实验。
