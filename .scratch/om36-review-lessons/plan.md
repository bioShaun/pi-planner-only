# Native 指令：修复合并与审查时机

日期：2026-10-31
状态：已实施；已审（reviewer 6829400e，CHANGES REQUESTED；两项 P1 与两项 P2 已按其建议修订）
依据：同目录 `findings.md`（om36 会话 01a18d37，Native 模式，插件版本 e1d0ab6，即当前 HEAD）

## 1. 意图

在 `NATIVE_PROMPT` 中补三条规则，只改指令文本，不改机制：

1. 按审查意见修复时，需共同维护同一状态一致性或锁协议的修复优先合并成一次委派。
2. 改变并发行为、锁协议或持久化状态一致性的交付及其修复，先经独立审查，再开展依赖这些改动的后续工作。
3. 派 reviewer 前写明待审范围和依据；reviewer 的工具取不到的材料，先导出为文件。

同时把原合并条件收紧为“同一成果中”，避免把“最后都跑全量测试”误读成共用验收命令。

## 2. 案例事实（摘自 findings.md）

- 修复拆成三轮：F1+F5、F2+F4 和 F3。前两轮改的是同一个 `fleet.py`，验收命令都是全量 pytest。Root 在拿到审查结论时就一次性定下了三轮计划，并不是因为子代理只交回了部分结果。现有规则没有写明怎样判断修复之间是否相互依赖；"共用同一验收命令"也容易被理解成"最后都跑全量测试"，从而失去区分作用。最终 Root 把这些修复分开派了。
- Root 对 #26 的三段交付只自查了 diff（"diff 没问题"）。四个 PR 全部叠完后才第一次派 reviewer，结果为 BLOCK，含 3 个 P0。#33 因此 rebase 了两次。
- builtin reviewer 的工具是 `read, grep, find, ls, watchdog_diff, contact_supervisor`，不能运行 git。`watchdog_diff` 只给出会话开始以来的 diff，给不出叠放分支的区间 diff。审查开始后 reviewer 通过 supervisor 求助，Root 才临时导出文件。
- "只交回部分结果时缩小范围"这条规则在 #26 上有效，三段都一次通过，本次不改。

## 3. 具体指令（替换后全文）

> 实现和跑测试优先交给子代理，自己负责拆分、检查 git diff 与测试结果。若你已掌握相关上下文，剩余修改与必要验证都明确、局部，且无需进一步调查、设计测试或独立复核，可直接完成修改与验证；否则继续委派。每次委派只交付一项可单独验收的成果，例如一个新模块或命令连同其测试；同一成果中共用一次验收或昂贵读取的步骤合并，互不依赖且可分别验收的成果分开委派。按审查意见修复时，需共同维护同一状态一致性或锁协议的修复优先合并；需等新事实或用户决定的项后派。子代理请求拆分或只交回部分结果时，先缩小本次交付范围再派，可续用原子代理，不要只要求它继续或在同一任务内分阶段；缩范围时沿用原模型，仍失败再换模型。改变并发行为、锁协议或持久化状态一致性的交付及其修复，检查 diff 与测试后先经独立 reviewer 审查，通过后再开展依赖这些改动的后续工作；自查与测试不能代替该审查。派 reviewer 前，写明待审范围和依据；其工具无法取得的 diff 或依据，先导出为可读文件并给出路径。

位置说明：

- 合并规则紧跟在原有拆分规则之后，作为它在审查修复场景下的具体化。
- 审查规则放在"缩范围"之后，表示一项交付验收之后的下一步。

## 4. 语义边界

1. **合并按语义依赖判断，不按文件判断。** 只有需要共同维护同一状态一致性或锁协议的修复才优先合并；同一文件里互不相关的修复仍可分开派。合并只限于“按审查意见修复”这一场景，新功能照旧按可单独验收的成果拆分（#26 的大包确实提前返回过）。
2. **合并后仍可缩范围。** “优先”不是强制。初次派发时如果已知合并后的包过大，可以拆开；交回部分结果时，照常适用缩范围规则。
3. **审查触发条件按改动语义判断，不按文件数判断。** 改变并发行为、锁协议或持久化状态一致性的改动，即使只改一个文件，也需要独立复核，因此不满足局部例外的“无需独立复核”条件。只改说明、日志或展示，不属于触发条件。
4. **“通过后再开展依赖的后续工作”是顺序要求，不是工具拦截。** 它适用于叠放 PR、同分支继续实现、下游采用新版本等情况。Native 仍是中性指令：不加工具，不做运行时检查。
5. **导出材料视 reviewer 能力而定。** 审查范围和依据始终要写明，提交区间写清 base/head；只有 reviewer 的工具取不到的材料才需要导出。这里不写死工具清单，因为它可能被 `agentOverrides` 覆盖。
