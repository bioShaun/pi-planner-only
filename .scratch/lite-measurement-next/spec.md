## Problem Statement

以下为2026-09-26制定计划时的背景；其中未完成或受阻状态已被上方最新进度取代。

维护者需要判断：在模型、任务和委派指引相同的条件下，lite 插件是否比原生 pi-subagents 提供额外价值，以及长会话交接是否值得继续维护。

目前 native 第三臂、计费与有效性守卫已实现，12 项离线故障测试和独立代码审查通过，但完整发布测试未完成，三臂真实试跑尚未启动。上次执行在创建仓库外临时目录时遇到只读文件系统错误。代码审查通过不能替代运行验证，也不能支持“插件更省钱”的产品结论。

历史 direct/lite 比较混合了插件与委派指引的效果；历史 0.48 比例又受模型重算和答案泄漏疑问限制。现在需要一轮边界清晰、预算有限、不会漏算失败与返工的比较，而不是恢复原来的 54 次 campaign。

## Solution

按下列顺序推进，每个阶段满足退出条件后才进入下一阶段：

| 阶段 | 要完成的工作 | 退出条件 |
|---|---|---|
| 1. 补齐运行前验证 | 解决临时目录访问条件，补跑完整发布测试，核对当前 bench 回归和 T3 标准答案证据 | 必需检查通过；版本、环境和检查结果可追溯 |
| 2. 冻结试跑条件 | 固定三臂、模型、提示词、任务、源码快照、随机顺序和预算 | 获得可复现的六次运行清单，未调用付费模型 |
| 3. 逐条试跑 | T3 × direct/native/lite × 各两次，串行执行，每次结束后由 Root 判断是否继续 | 完成最多六次尝试，或明确触发停止条件并保存证据 |
| 4. 给出首轮结论 | 汇总有效性、通过率、所有尝试费用、耗时、人工介入和机制指标 | 明确链路是否可靠、是否需要修复或值得扩样本，不发布节省比例 |
| 5. 有条件启动 handoff | 在真实长会话检查点比较继续原会话与主动交接 | 满足启动门槛后完成一对试跑，或记录不满足条件而延后 |

若资源、权限、计费完整性或任务质量出现问题，停止后续付费运行。保留失败证据，不通过替换任务、增加重试或静默排除失败来凑齐样本。

## User Stories

1. 作为维护者，我希望知道哪些准备工作已经完成，以便把下一步精力放在尚未取得的运行证据上。
2. 作为维护者，我希望完整发布测试先通过，以便避免在已知回归尚未排除时消耗模型额度。
3. 作为执行本计划的 Root，我希望先确认临时目录、网络和模型访问条件，以便区分环境阻塞与实现缺陷。
4. 作为维护者，我希望保存准确的源码和运行环境快照，以便重复实验时能解释结果差异。
5. 作为维护者，我希望标准答案能够通过同一套评测，以便失败结果确实反映任务完成情况。
6. 作为维护者，我希望任务克隆不含标准答案提交，以便模型无法直接检出答案。
7. 作为维护者，我希望同时比较 direct、native 和 lite，以便分离委派指引与插件的贡献。
8. 作为维护者，我希望 native 与 lite 使用相同模型和委派指引，以便减少对照条件的差异。
9. 作为维护者，我希望先测非 strict lite，以便不把强制委派规则混入默认模式的结论。
10. 作为维护者，我希望固定任务并交错运行三臂，以便减少任务选择和运行顺序带来的偏差。
11. 作为维护者，我希望最多执行六次尝试且不自动重试，以便控制初轮成本。
12. 作为执行本计划的 Root，我希望每次运行结束后检查预算和结果，以便在出现问题时停止下一次请求。
13. 作为维护者，我希望失败、未完成和返工的费用都可追查，以便不只看到成功样本的低成本。
14. 作为维护者，我希望缺失元数据、用量或退出证据时总费用保持未知，以便不把漏记当成节省。
15. 作为维护者，我希望恢复子会话与重复上报能被区分，以便既不漏算新运行，也不重复计费。
16. 作为维护者，我希望遇到尚不能完整计价的嵌套委派时暂停测量，以便避免 native 对照被系统性低估。
17. 作为维护者，我希望并列看到质量、费用、耗时和人工介入，以便不为了省 token 牺牲任务完成质量。
18. 作为维护者，我希望将按模型价计算与 opus 权重重算分开展示，以便不把重算数字误认为实际账单或额度。
19. 作为维护者，我希望首轮报告明确小样本的用途，以便不依据两次重复就宣布插件节省比例。
20. 作为维护者，我希望三臂链路可靠后再决定扩样本，以便不在计费缺口上扩大投入。
21. 作为维护者，我希望 handoff 使用自然达到阈值的真实任务，以便实验反映实际工作需要。
22. 作为维护者，我希望两条 handoff 分支从编写简报前的同一检查点开始，以便将交接准备成本计入比较。
23. 作为维护者，我希望两个分支的会话、工作树和产物彼此隔离，以便避免答案污染对照。
24. 作为维护者，我希望计入交接后的重新探索、遗漏和修复，以便评估完成任务的总成本。
25. 作为维护者，我希望先验证交接本身，再研究 confirm/auto 体验，以便不同时改变多个变量。
26. 作为维护者，我希望没有合适样本时可以延后 handoff，以便不为完成计划而制造长上下文或消耗额度。

## Implementation Decisions

### 1. 补齐验证，不重做已完成的实现

- 本轮以已有三臂运行入口、有效性检查器、费用汇总器和离线故障测试为基础，不另建调度器、任务账本或新的 agent 角色。
- 首先重新确认执行环境。此前的只读错误是上次运行的事实，不假定后续会话仍有相同权限；若命令被沙箱阻止，按当前工具权限流程申请必要的执行权限，不绕过沙箱。
- 在满足项目临时目录约束的环境中补跑完整发布检查。当前 bench 回归也必须对应最终冻结版本；失败时只修复实际发现的问题，修复后更新验证与审查证据。
- 对 T3 复核任务、源仓库、测试来源和 Python 环境。已有 goldcheck 可在条件一致且证据充分时复用；无法证明一致或发生漂移时重跑 goldcheck，不将历史通过直接当成当前通过。
- 不重复已有 native 实现；嵌套委派目前仍不可完整计价，作为明确停止条件保留。是否补充嵌套计费由真实试跑证据决定，不在启动前继续扩展实现。

### 2. 冻结唯一一组试跑条件

| 条件 | 决定 |
|---|---|
| 任务 | T3，三臂使用同一提示词正文和验收条件 |
| Root | 固定 cpass-ds，记录完整模型标识 |
| direct | 使用 direct-pds，不加载插件或 pi-subagents |
| native | 使用 native-pds，只加载 pi-subagents |
| lite | 使用 lite-pds-head，同时加载 pi-subagents 和当前插件 |
| native/lite 指引 | 相同中性委派前缀，不在前缀中指定不同工具名 |
| 子代理配置 | 同一运营者配置，记录实际使用的角色与模型 |
| lite 模式 | strict 关闭，handoff 关闭 |
| 重复与并发 | 每臂两次，最多六次尝试，串行 |
| 顺序 | 使用既有 campaign 的确定性随机顺序并保存清单 |

- 固定插件提交、bench 最终源码、任务、评测、计价表、宿主版本和子代理配置。bench 未提交时同时保留基线、完整补丁以及新增文件的内容与哈希；仅保存提交号或不含新增文件的差异不足以复现。
- 每次从干净的 parent 可达历史准备任务克隆，仅按任务定义加入目标测试。保留目标答案提交不可访问的检查证据，不能仅依靠日志关键词检查证明没有答案泄漏。
- dry-run 只用于准备与核对，不视为真实验证成功。顺序准备完成后逐次调用单次运行入口，不直接启动整组后台 lane。

### 3. 预算与停止条件

- 最多六次任务尝试，每次最多一次，不自动重试或 resume。失败和无效尝试同样占用次数，不另补样本。
- 每次结束后累计所有已发生尝试的任务成本。按冻结计价表的 opus 权重累计达到 $10 时，不启动下一次。这是运行间的检查点预算，不是单次调用的实时硬限额，也不是 ClinePass 的额度或实际账单。
- 执行中的单次运行沿用现有 3600 秒时限；不把提示词预算或子代理 token 限制宣称为可靠硬预算。
- 本轮不发起重复的付费健康请求，启动前使用不调用模型的配置与模型列表检查。若未来确需健康请求，其消耗必须另记，不能遗漏在实验总开销之外。
- 每次重任务前记录资源 audit/status 并判断结果，通过后使用 slot；遇到绕过 slot 的重进程不擅自终止或覆盖冲突检查。
- 任一 API/额度错误、质量验收失败、答案引用、未确认的子任务终态、费用或模型缺失、日志/元数据/退出证据缺失、嵌套委派计费缺口，以及无法确认的资源冲突，都停止后续运行。
- 停止后由 Root 保存原因、已发生消耗、剩余运行和最小修复方向。没有全部六次也可以形成完整的阶段记录，但不能声称已经完成三臂有效比较。

### 4. 首轮结果与扩样本决策

- 同时报告尝试数、有效运行数、通过数和未完成数，不能只给成功样本的费用均值。
- 主指标为任务通过率、包含失败与返工的费用、耗时及人工介入。Root 轮数、读取次数、cache-read、委派次数和截断等只用于解释结果；native 不支持的插件专用指标显示不可用，不显示成零。
- 分别保留按模型价计算和按 opus 权重重算的结果，注明计价表来源。前者也只是按记录用量与价格表计算，不冒充供应商结算凭证。
- 已知费用下界与完整总费用分列；未知总费用不能参与节省比例计算。本轮禁止重试，因此不应产生需要另行计价的归档尝试；一旦存在，必须披露并补齐，不能静默忽略。
- 六次试跑用于检验测量链路、任务完成情况和明显返工，不足以发布节省比例、稳定通过率或模型能力排序。
- 报告必须给出一个下一步决定及证据：修复测量后重订试跑、扩大固定样本、重新评估插件增量价值，或暂缓投入。扩样本的数量、预算和目标 Root 校准另定，不自动启动。

### 5. Handoff 的后续入口

- 三臂首轮有效比较完成、费用链路可靠后才考虑启动；不要求等待全部扩展重复完成。
- 必须有正常任务自然越过默认上下文阈值，且仍有实质工作未完成。不降低阈值或填充无关内容制造样本。
- 先验证宿主能恢复并隔离同一个检查点的会话、工作树、工具产物和验收目标。当前只存在测量协议，不宣称 bench 已实现会话分叉。
- 检查点放在编写交接简报之前。一臂继续原会话；另一臂由操作者主动请求交接。两臂自动交接都保持关闭，并使用相同插件、模型和剩余任务。
- 单独报告共享前缀与检查点后的增量成本。增量包含简报准备、新会话加载、重新探索、遗漏修复、子代理与失败尝试；共享前缀不重复计入配对增量。
- 先计划一个检查点的一对试跑，预算和时间上限在启动前按任务确定，不沿用三臂预算也不视为无限授权。确认恢复、隔离、计费和质量可比后，再决定重复次数。
- confirm/auto 的自动触发与确认体验留待交接本身值得继续验证后另测。没有合适任务就延后，默认 off 不变。

## Testing Decisions

**测试边界沿用已讨论并采用的端到端入口：单次任务运行 → 结果有效性与质量检查 → 费用汇总。** 优先从这一个边界验证外部可见行为，不为本计划新增内部 hook 或逐函数验收接口。

- **完整发布检查**：在仓库外、符合项目约束的 TMPDIR 下运行 `npm run test:release`。要求 typecheck、contract、git、delegate、host、index 全部通过且没有必需检查被跳过。上次仅 typecheck/contract 和单独的 host 通过，不足以替代本项。
- **bench 离线故障回归**：沿用现有 12 项测试。它们验证加载边界、有效性、计费结果和故障处理，不以实现者自述或内部函数名作为通过依据。新增守卫必须有能单独触发该故障的测试，健康 Root/子任务用量不能同时被破坏而掩盖被测守卫。
- **完整性场景**：覆盖单个、并行和链式原生结果；新 run 恢复旧 session 与同 run 重复上报；未知模型、缺失/损坏用量、嵌套委派、悬而未决的调用、元数据缺失、JSONL 截断、退出记录缺失和非零退出。应观察到明确无效或未知总费用，而非低估的完整数字。
- **历史兼容**：已有正常 T3 冒烟日志在新汇总器下应保持相同费用与机制指标；这只说明汇总兼容，不构成新三臂实验结果。
- **任务质量**：复用目标测试与 masked suite 的标准答案/验收流程。要求目标测试通过且没有相对已知基线的新增失败；同时保留进程退出码、完整评测日志和实际差异，不能只相信一个 pass 字段。
- **真实链路**：最多六次运行本身就是首轮宿主验证，不再叠加一套付费冒烟。每次都检查实际加载条件、终态、用量、质量和人工介入；离线路由测试通过不能替代真实宿主证据。
- **handoff 场景**：使用同一检查点和相同最终验收，验证分支隔离、完整会话链及所有后续成本。暂不实现或测试分叉基础设施；启动门槛达成后，优先使用宿主已有的会话恢复能力。
- **验收记录**：将代码审查、离线回归、完整发布检查、真实试跑分别记录。只有当前范围所需证据齐全才能宣称该阶段完成；保留每次失败与修正，不覆盖成一份“全绿”摘要。

## Out of Scope

- 重做已完成的 native 第三臂实现，或为此恢复复杂调度、持久化任务账本和固定多角色审批流程。
