# 04：G1/G2 场景重设计

Status: needs-triage
Type: task

Source: `../campaign-report.md`（"场景限制"一节）、`../spec.md`。

## 背景

票 03 的场景回放没能在任何受测模型上重现三个目标故障模式（误派 validator、子任务超时、同轮重复等待），包括在原始故障模型（Astra、Sonnet）上。结论不是"票 01 无效"，而是"场景没有给出失败的机会"。要评估票 01 或未来的指导改动，需要重新设计场景。

## 已知限制（票 03 报告逐条确认）

1. **G2.md 提示泄底**（commit `6f66f6c`）：题目写明"用 `slot cpu -b` 后台提交"，测不了拆分决策，只测等待方式。
2. **G2 触发不了子任务超时**：Root 自己用 bash 前台跑不受 child 时限约束（flash pilot 实例）。
3. **G1 诱导强度不够**："审计/核对"措辞在 flash、gpt-6-sol、Astra 上都没诱发误派。
4. **bench 环境自带纠偏**：全局 AGENTS.md 的 slot 规则进入 Root 提示，部分故障机会在场景外被消除；且不同 Root 对规则的遵守程度本身是个变量（flash 看到规则仍前台跑）。

## 重设计方向（讨论起点，不是决定）

- G1：把"写文件"属性藏进长任务中间（例如主要诉求是核对/分析，交付物清单里夹一个必须由脚本生成的汇总文件），而不是在标题里写"产出文件"。
- G2 拆成两个场景：
  - 测拆分决策/超时：不在题目里提示后台提交；用 strict 模式（Root 不能自己跑 bash，只能委派）或把运行时长拉到前台不可接受的程度，让"child 前台顶着时限跑"成为真实的失败路径。
  - 测等待方式：保留后台作业，但去掉"先 slot audit 再提交"这类步骤提示，只留全局规则。
- 考虑加一个"故障注入"对照：如果场景设计上就复现不了，可以反向构造一个必然诱导错误行为的变体（如明确暗示"派 validator 去生成"），用来校准场景灵敏度——连这个都不失败，说明场景太弱。
- 评估矩阵按"故障 × 原始模型"组织（Astra→误派、Opus→超时、Sonnet→同轮重复等待），base 先行、重现才跑 treat 的两步流程沿用票 03 的做法。
