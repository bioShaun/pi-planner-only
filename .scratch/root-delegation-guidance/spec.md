# Root 委派指导：派任务、等待与验收

Status: ready-for-agent

来源：`.scratch/om09-usage-20260929/findings.md`（2026-09-28 至 09-29，两台机器，44 个业务会话，104 次委派请求）。

## Problem Statement

用户在真实业务项目里用 Lite 模式时，Root 派任务、等待长时间运行、验收结果这三个环节会浪费时间，也会留下验收缺口。这些问题和 Root 用哪个模型无关：

- **角色和交付物不匹配。** 要求"创建审计脚本并输出 JSON/TSV"的任务被派给了 validator。validator 不能写文件，但 Root 看到的角色说明只有"runs checks"。76 秒后，子任务以 `completed` 结束，报告正文却说没有复算、也没写产物。Root 只好改派 worker，worker 又超时了。
- **长时间运行塞进了一个子任务。** Opus 在玉米项目里的两次 600 秒超时，child 工具运行分别占约 533、352 秒。提示只说"超过时限就拆分"，没说运行本身就超过十分钟时怎么处理：流水线、构建、全量重算都没法再拆。
- **Root 阻塞等待，还重复等待。** 含显式 sleep 的 Root 命令窗口，Opus 合计约 60.9 分钟，Sonnet 约 183.5 分钟。Sonnet 在同一条 assistant 消息里发出过 3、2、6、5 条完全相同的等待命令，其中 6 条 `sleep 598` 几乎同时返回。
- **把 `completed` 当成验收通过。** `completed` 只表示子调用正常结束。Sonnet 会话里两份 reviewer 报告称拿不到有效的 HEAD 基线：reviewer 没有 shell，只能看到未提交的改动，改动一旦提交它就看不到差异。

四次超时原因各不相同。本机 Sonnet 那次工具区间只有约 33 秒，却有 46 个 child 轮次。所以统一延长 timeout 不对，换 Root 模型也没有证据支持。

## Solution

只改 Root 看到的指导内容，不加运行时机制，也不改 child 行为：

1. **委派前核对交付物和角色。** 需要写脚本、生成文件或报告的任务派给 worker。validator 只运行已有检查，不写文件。
2. **超过子任务时限的运行分成两次委派。** 先派"实现并启动后台作业"：worker 启动作业后立即返回作业标识、输出路径和完成条件。运行结束后，再单独派一次验收。
3. **等待不阻塞、不重复。** 同一个作业只留一个观察入口，每次只发一条有界的状态查询，不在同一轮发出相同的等待命令。
4. **验收分层说明。** `completed` 只是生命周期状态。Root 在答复里区分"实现完成""检查通过""真实运行通过"。reviewer 提出的必修问题要有修正证据。审查已提交的改动时，在任务里写明基线 commit。

提示长度上限保持不变。新增内容主要放在 `delegate` 工具的说明里。

## User Stories

1. 作为 Root，我想在委派前就知道哪个角色能写文件，避免把产物任务派给只读角色。
2. 作为 Root，我想从 `role` 参数说明里直接看到"validator 只运行已有检查、不写文件"，不必从失败里反推。
3. 作为 Root，交付物是脚本、报告或输出文件时，我想被明确引导去派 worker。
4. 作为 Root，我想知道子任务时限针对的是 child 主动工作的时间，超过时限的运行应该移到后台作业里。
5. 作为 Root，我想要一个固定的两步做法：先派"实现并启动"，拿到作业标识、输出路径和完成条件，再派"验收"。
6. 作为 Root，我想让 worker 启动长运行后立即返回，别在子任务里等运行结束直到超时。
7. 作为 Root，我想在任务文本里写明完成条件（输出文件、退出码、日志标记），让后续验收有据可查。
8. 作为 Root，等待后台作业时，我想每次只发一条有界的状态查询，不发一批相同的 sleep。
9. 作为 Root，我想在作业还没结束时先把当前状态告诉用户，不把整个会话卡在一条长 sleep 上。
10. 作为 Root，我想记住 `completed` 不等于验收通过，按报告正文和检查输出判断。
11. 作为 Root，我想在最终答复里分清"实现完成""检查通过""真实运行通过"，别把没跑过的流水线说成已验证。
12. 作为 Root，reviewer 给出 `CHANGES REQUESTED` 时，我想在修正后留下对应的修正证据，再结束。
13. 作为 Root，改动已经提交时，我想在给 reviewer 的任务里写明基线 commit，或附上 `git_audit` 的 diff 结论，让它有比较基准。
14. 作为 Root，reviewer 报告拿不到基线时，我想把它当成审查缺口，而不是审查通过。
15. 作为 Root，子任务超时后，我想先检查已有产物和最后的工具结果，再只补派剩余工作。
16. 作为 Root，我想在超时后先判断属于哪一类（运行占满时限、任务范围或轮数过大、模型响应慢），再决定拆运行、缩小范围还是补上下文。
17. 作为用户，我想让长流程运行期间 Root 仍然能及时回应，而不是沉默十几分钟。
18. 作为用户，我想看到清楚的验收层级，自己决定还要不要做真实运行验收。
19. 作为用户，我想少看到"角色不匹配 → 空转 → 改派 → 超时"这样的连锁。
20. 作为维护者，我想让插件系统提示的长度保持在现有上限以内，不放宽已有断言。
21. 作为维护者，我想让新增指导都能用单测断言到，防止以后重写时被悄悄删掉。
22. 作为维护者，我想用固定场景回放比较改动前后的插件版本，用数据判断这次改动有没有用，而不是靠自然出现的少量样本。
23. 作为维护者，我想同时看反向指标（委派次数、Root 自己动手的次数、总用量），确认改动没有造成过度拆分。
24. 作为维护者，我想让评估保持 Root 模型、child 模型和验收标准不变，只改插件版本。
25. 作为 strict 模式下的 Root，我想看到同样的角色、长运行和验收指导，因为 strict 下我更依赖委派。
26. 作为运营者，我想让这些指导不依赖某台机器特有的命令名，在别的机器上也能用；本机的 `slot -b` 只作为示例出现在业务任务里，不写进插件文本。

## Implementation Decisions

- **只改 Root 看到的指导内容。** 涉及三处：`plannerPrompt` 的输出（strict 与非 strict）、`delegate` 工具定义的 description、`role` 参数的说明。不改 child 的收尾指令、宿主超时、锁或 git 摘要。
- **提示长度上限不变。** `plannerPrompt` 两种模式都保持在现有 1,700 字符上限以内（当前非 strict 1,662、strict 1,678），不改这条断言。
- **`plannerPrompt` 只改角色那一行。** 在 validator 的描述里加一个短语，表明它不写文件，例如"`validator` runs existing checks and writes nothing"，措辞由实现者在上限内决定。其他已被正则固定的句子不改原文。
- **其余新增内容放进 `delegate` 工具的 description。** 追加在现有文字之后，保持现有断言匹配的句子原样。要覆盖四点：
  1. 交付物需要写文件时用 worker；
  2. 超过子任务时限的运行分两次委派，先"实现并启动后台作业，返回作业标识、输出路径和完成条件"，再"运行结束后验收"；
  3. 等待后台作业时，每个作业一次只发一条有界的状态查询；
  4. `completed` 只表示子任务结束，答复里要区分"实现完成、检查通过、真实运行通过"。
- **`role` 参数说明补两点。** validator 写明"只运行已有检查，不写文件"；reviewer 在现有"sees files and uncommitted changes"之后补上"改动已提交时，在任务里写明基线 commit"。
- **措辞与机器无关。** 不出现 `slot`、`nextflow` 等本机命令名，统一说"后台作业（background job）"和"有界状态查询（bounded status check）"。
- **时限数字从现有配置取。** 如果 description 里要写时限数字，就沿用 `plannerPrompt` 取 `timeoutMs` 的方式，不写死"10 分钟"。工具定义目前是静态的，用不上配置时就只写"the child time limit"。
- **不加运行时拦截器。** 不去重相同的 bash 等待命令，也不拦截派给 validator 的写任务。这两个问题报告里只证明了存在，没证明需要机制来解决。
- **文档同步。** README（中英两版）里讲角色或委派方式的段落，与新指导不一致的就同步。CHANGELOG 记一条。

## Testing Decisions

- **只测外部可见的指导内容。** 对 `plannerPrompt(false)`、`plannerPrompt(true)` 和注册后的 `delegate` 工具定义，用正则断言新指导存在，不断言整段原文。
- **测试模块是 index 套件。** 先例是 index 测试里现有的提示词断言：prompt 长度、`A child has N minutes`、角色描述等正则，以及对 `h.tools.get("delegate").description` 的断言。
- **新增断言至少覆盖：**
  - 两种模式下 validator 都标明不写文件；
  - `role` 参数说明里 validator 不写文件，reviewer 需要基线 commit；
  - `delegate` 的 description 包含写文件派 worker、长运行分成启动与验收两次委派（带作业标识、输出路径、完成条件）、每个作业一次一条状态查询、`completed` 不等于验收；
  - `plannerPrompt` 两种模式仍少于 1,700 字符。
- **故障注入。** 仓库规则要求新增防护时补故障注入检查。这次没有新增运行时防护，只有文本，所以用"删掉某句指导后断言失败"作为自检：实现者在报告里写明手动试过。
- **不删除、不放宽已有断言。** 用 `git diff` 检查被删除的 `assert` 行，结果必须为空。
- **静态开销。** 用 `bench/overhead.mjs static --ref HEAD` 对比工作树，把提示和工具定义增加的字符数写进实现票的报告。
- **行为效果交给 bench 场景回放（票 02、03），不放进单测。** 单测只保证指导存在、长度不超。

## Out of Scope

- 更换或调整 Root、child 模型及思考强度。
- 优化重复读取、派发启动开销。报告显示调用包络减 child 时长的中位数都不到 0.4 秒。
- 延长或按角色区分子任务 timeout。
- 运行时去重相同的等待命令、拦截角色不匹配、提供新的后台作业工具或轮询工具。
- 修改 child 的收尾指令，包括 validator 的"Do not modify any files"。
- 上游 502/503 等提供方故障的重试策略。
- 在远端机器上复核历史业务改动或停止远端运行。
