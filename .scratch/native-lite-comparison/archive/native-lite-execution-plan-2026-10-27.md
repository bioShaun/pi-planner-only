## 目标与范围

确定 Native 和 Lite 各自适合的任务范围，比较委派与编排方式的质量、用量、时间和人工负担。
不预设任何一方更快或更便宜，也不把并行能力当作 Native 独有特征。
Lite 支持独立且锁兼容的并行；同 cwd 单写者，同仓库 worker 与 validator 不并行。
实现完成后，validator 与不依赖其结果的独立源码 reviewer 可有条件并行。
两模式都采用各自合理的最小编排，不用人为串行的一方对照人为并行的另一方。
必要的模式差异保留并明示；对 Root/child 模型、thinking、工具和配置作可核对的控制或差异记录。

### 交接检查点

P1 执行前：

- 记录当前 HEAD、index、已跟踪及未跟踪状态，不清理既有未跟踪文件。
- fetch 后记录远端 SHA 和共同祖先，再审查远端提交及净 diff。
- 从已验收 SHA 建立仓库外 worktree 和独立集成分支，保留来源 SHA。
- merge 后检查父提交与净差异，判断已有 release 证据是否仍适用。
- 由 Root 决定是否更新本地主分支；冲突和新增产品变化先停下。

P2 归档前：

- 区分已提交记录、未跟踪研究、机器本地临时证据和未来产物。
- 保存可公开的来源、指纹、关键结论和证据局限，不改写历史红绿记录。
- 核查日志是否含隐私或其他任务数据，必要时仅保留最小摘要和指纹。
- 证据入口单独提交，避免将研究资料混为已实现功能。

P3 启动前：

- Root 为每场景写明决策问题、候选范围和统一接受条件。
- 记录两臂是否有相同模型和工具能力，以及不能消除的差异。
- 明确超时、费用止损、故障重试和实际授权；未冻结不得启动实验。
- 给每臂分配独立目录、会话和证据路径，并核验基线一致。
- 明确候选匿名化是否可行，若不可行则记录审查偏差风险。

P4/P5 收尾时：

- 逐任务记录实际选择模式的原因，不事后挑选成功案例。
- 记录安装版本、会话加载状态以及实际发生的 supervisor 行为。
- 若真实请求没有出现，标记未验证，不构造成功记录。
- 按需要归档错误及阻断，不把观察结果包装成实验对照。

P6/P7 收尾时：

- 核对两臂的 baseline、brief、标准和各自完整 manifest。
- 按统一标准独立验收每个候选，保留未通过和环境故障。
- 单独记录人工准备、调度、返工和 Root 最终验收。
- 决策前评估补测是否能区分尚未解决的问题及是否仍在止损内。

P8 输出时：

- 按任务类别说明建议、证据强度、例外和仍未知的条件。
- 分别列出同步、安装、push、release 的状态及其前置条件。
- Root 核查是否需要新授权；已有授权范围内不重复设置机械批准门槛。
- 不将建议等同于安装、发布或部署已经完成。

## 调度与职责

```text
Root 冻结范围、brief、基线与验收
  → 一个写者实现并固定候选、manifest 和 diff
  →〔受影响验证 ∥ 独立源码审查〕（仅在条件满足时）
  → Root 核对同一版本、实际 diff、检查结果与审查发现
  → 需要修复或集成时才启动一个写者 → 重新冻结并复验
  → Root 最终接受或拒绝
```

- 简单有界任务使用一个 child；不为了制造并发增加角色或预启动等待批准的 child。
- 只有候选固定、验证不修改候选源码、reviewer 不等待验证结果时才并行。
- 若验证可能写源码，先改为隔离副本或串行；临时输出放外部目录。
- reviewer 应有独立新上下文；若最终需要核对测试日志，Root 汇总时另做证据核对。
- 异步运行依靠完成通知；有安全的独立工作就继续，否则让出，不为普通 child 轮询或 sleep。
- 启动、工作流、child 或工具配置失败时保存部分 diff、状态与原因，按同一协议报告并谨慎重试；不静默切换 CLI。
- 调度日志记录实际开始、结束和可证明的重叠；存活区间包含等待，不等于模型计算时间。
- Native workflow 是显式依赖和 fanout 的工具，不自动发现并发；容量限制和资源竞争可能导致排队。

## 对照协议

P3 在启动前建立可复核的协议，至少冻结以下项目：

1. 场景 ID、真实任务来源、共同 baseline SHA、初始工作树与依赖指纹。
2. 完全相同的任务 brief、允许编辑范围、验收标准和测试要求。
3. 每臂独立 worktree 和新会话；运行期间不读取另一臂的产物或结果。
4. Root 第二臂使用未看过第一臂解答的新上下文，避免从第一臂带入方案。
5. Root 和各 child 的 provider、具体模型 ID、角色映射、声明 thinking 和实际可见切换。
6. strict、handoff、context 配置，skills、可用工具、宿主和插件版本及安装来源。
7. 每种模式的最小合理编排、不可消除的模式差异、明确可比和不可比项。
8. 首臂次序、时间和费用止损、最大尝试次数、任务授权和故障处理规则。
9. 候选保存、统一验收、可行时匿名化审查、Root 接受及生产集成规则。
10. 环境、缓存状态和资源竞争记录方法，以及可见用量的覆盖范围。

实际任务、模型 ID、超时和费用止损均待填，不在本文虚构数值。
Root 在既有授权范围内确认并冻结协议；不机械要求用户对已授权工作再次批准。
首批最多三对，每场景至多一对额外补测；这些是数量上限，不替代费用和时间止损。
可执行的比较应交替安排首臂；有决策价值的补测交换次序，记录顺序效应。
资源干扰、缓存冷热与共享状态只能记录和尽量控制，不声称缓存完全可控。
不同模式固有工具或生命周期差异必须保留并注明；不能把所有结果解释为单一机制的因果效应。
日常观察是观察性记录；配对也可能受顺序、样本和环境限制，结论按实际控制程度表述。
候选可匿名化时，以相同标准盲审以减少偏差；功能正确性和质量先于速度、费用。
真实生产任务只集成 Root 接受的一个候选；实验副本不向外部系统写入。
失败、超时和未完成均保留；环境故障单列并记录证据，不能悄悄剔除或按零计。

## 可复制记录模板

以下模板用于每一候选和每次运行；未取得数据写 `unknown` 并说明原因，不以零代替。

```yaml
pair_id: 待填
scenario_id: 待填
candidate_id: 待填
run_id: 待填
mode: Native 或 Lite
baseline_sha: 待填
candidate_manifest: 路径、算法、指纹及覆盖范围
worktree_and_session: 标识及隔离方式
versions: 宿主、插件、pi-subagents、依赖及来源
config: Root与child模型、角色、thinking、strict、handoff、context、skills、工具
order_and_environment: 顺序、资源竞争、缓存状态和已知差异
start_end: 用户请求开始、各阶段开始结束、Root最终验收结束及时间基准
acceptance: 结果、标准、检查退出码、审查发现和Root实际diff核对
root_interventions: 次数、时间、原因及操作
rework: 次数、原因、新候选指纹和复验范围
overlap: 实测区间、证据及未知边界
usage_coverage: Root与各child分别列input、output、cache读写及缺失项
cost: provider记录或估算、来源、计价口径、覆盖与unknown
failure: 终态、环境故障、止损、部分结果及未完成原因
evidence_paths: manifest、日志、diff、审查和验收记录
```

每对汇总两臂的候选、验证、Root 最终接受或拒绝和所有失败，不只列胜出者。
用户端墙钟从请求开始到 Root 最终验收完成，包括等待和协调；截断时标明未完成。
单列准备、人工调度、运行和最终验收时间及其区间，避免把重叠阶段相加当墙钟。
模型计算时间与 child 生命周期不同；缺少可直接测量的计算区间就标 unknown。
Root 与 child 的 input、output、cache read/write 分列，明确各自覆盖和缺漏。
费用保留 provider 记录或估算及其来源，不把日志价格冒充实际账单。
Native 状态栏 child 数字是已记录下限，Lite 用量覆盖不同，不能直接比较两边状态栏费用。
零记录不证明免费；未知不当零，只有口径和覆盖可比时才计算百分比。
单 pair 逐项报告，不夸大统计显著性，也不将异质样本合成普遍成功率。

## 验证、复用与资源

- 先绑定候选 manifest、源码、测试、锁文件、相关依赖和验证环境；仅在这些与原证据相符且检查适用时复用 full release。
- 每个不同候选分别运行其受影响检查，不能借另一候选的绿灯；证据明确绑定候选版本。
- 修复先取得针对真实缺陷的红灯，再验证绿灯；新增 guard 包含能触发该 guard 的 fault injection，不删弱既有断言。
- Root 读取实际 diff、命令输出与退出码，不仅采信 child 报告；来源不完整时记录边界。
- 纯文档任务只检查链接、一致性与 diff，不跑产品测试；产品改动按风险和项目规则执行检查。
- 仓库外临时目录使用 `/project/tmp` 下任务目录，禁止 `/tmp`；完整日志保存真实命令、cwd、环境、时间与实际 exit。
- 预计超过 1 分钟、超过 2G 或大量 `data_0` 读写的任务先读 `~/.config/agents/slot.md`。
- 重活先执行 slot audit/status 并保存日志，再按规则通过 slot 运行；不从意图推断命令已经成功。
- 最多四个并行工具调用；并发检查也要遵守资源槽、候选隔离和单写者限制。
- 默认全局 peer 限制存在时记录隔离入口及其包指纹，不把隔离测试称为全局安装已修复。

## 退出、重冻结与暂缓

- 每阶段以表中验收为出口；缺失必需输入、权限、预算边界或证据时标 `blocked`，记录原因与恢复条件。
- 任务、baseline、模型、配置、验收规则或环境发生实质变化时暂停并重冻结协议；旧结果保留，不混入新组。
- 新产品修改使受影响 pair 的基线及证据重新评估；不得把不同版本结果当同一组。
- 测试或审查要求修改候选时先结束旧候选审查，固定新 manifest，再重新运行受影响验证和审查。
- Native 自动 handoff、`check` v1、遥测实现、thinking 单变量对照与并行写继续暂缓。
- 研究记录和实验结论不混入功能提交；引出新产品需求时另行定义范围与验收。
- 分支同步、运行安装更新、push 和 release 是独立动作；任何阶段都不自动部署或 reload。
- 证据不足时最终建议应明确 unknown 或暂不选择，而不是为完成计划扩大实验。
