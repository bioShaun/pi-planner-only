# 借鉴 subagent-split-check：拆分判据与测量纪律

来源：MiniMax-AI/mcode-stack `stacks/ronny/skills/subagent-split-check/SKILL.md`（main 分支，2026-10 读取）。本 spec 只记录对本仓库可迁移的部分；各项按阶段推进，改变 Root 行为的条目必须先有测量证据。

## Problem Statement

该 skill 的立场是“子代理用来管理上下文，不用来划分地盘”：默认单主循环，只有在可测量的上下文退化、可并行且可丢弃的工作、工具或指令冲突三种情形下才拆分，并以“后续需要原始中间输出，还是只需要结论”作为单步判据。

本仓库拆分的首要理由不在这三条之内：Lite 让 Root 用贵模型规划和验收，Child 用便宜模型干活（成本套利）。因此不能照搬“默认不拆”，否则等于否定插件本身。但对照这个 skill，可以看到本仓库的几处缺口：

1. Root 判断“自己做还是委派”主要靠文件数和时长（约 ≤2 个文件、≤10 分钟）。按上下文边界看，这只是代理指标；仓库自己的调研（`docs/research-root-task-decomposition-2026-09-28.md`）也说文件数只能当提醒。
2. 不同角色的交接损耗差别很大，但现有指引没有区分：Explorer 和 Validator 只需返回结论或“命令＋退出码”，正适合拆分；Worker 的结果必须由 Root 看 git diff 和检查输出才能验收，交接后 Root 要重读原始材料。
3. Native 指令是无条件的“实现和跑测试交给子代理”，没有小任务例外，和 Lite 的规则不一致。
4. Worker 之后紧跟 Validator：两者先后调用、在同一仓库互斥持锁、读写同一份数据，正是该 skill 所说“最应优先考虑合并”的组合。但单独的黑盒验证本身又是该 skill 认可的合理拆分。目前没有证据能在两者之间做出判断。
5. 基准测量与该 skill 的纪律有差距：近期结论多来自每组每任务一次运行（如 T2c）；汇总给出了成本比和每任务通过数，但没有给出各任务通过/失败相对基线的翻转情况。
6. 新增或调整角色、机制时，没有统一的拆分决定格式。

约束：Lite 的 `plannerPrompt` 现有长度为 1,498（非 strict）和 1,489（strict）字符，测试上限是 1,500（只有测量证明有收益才能放宽）。任何提示词补充都必须同时删去等量文字，或另附放宽上限的测量证据。

## Solution

分三个阶段推进，先做不改变行为的部分：

- **阶段 A（不改行为）**：
  - 在基准汇总里加入按任务的通过/失败翻转视图。
  - 当某组某任务只有一次有效运行时，在汇总中明确标注。
  - 制定拆分决定记录格式，供以后提新角色或新机制时使用。
- **阶段 B（离线设计，暂不付费运行）**：
  - 设计“Worker 自测、Root 看输出”与“Worker 加独立 Validator”的对照实验。
  - 设计 Native 指令加小任务例外的对照实验。
  - 两个实验都只写方案和所需预算，不运行。
- **阶段 C（有证据后才改行为）**：根据阶段 B 的测量结果，决定是否把“需要原始输出还是只需结论”的判据写进 Lite 指引（替换文件数启发式的一部分），以及是否修改 Native 指令和 Validator 的使用建议。

## User Stories

1. 作为维护者，我希望汇总能按任务列出相对基线由通过变失败或由失败变通过的情况，以免总通过率或平均成本掩盖个别任务的退化。
2. 作为维护者，我希望某组某任务只有一次有效运行时，汇总能显式标注，以免把单次运行当成稳定结论。
3. 作为维护者，我希望翻转视图同时出现在文本输出和 JSON 摘要里，以便归档并供后续比较。
4. 作为维护者，我希望无效运行和未评测运行不参与翻转判定，与现有统计口径一致。
5. 作为维护者，我希望同一任务在某组内结果有过有不过时，翻转视图标为“不稳定”，而不是强行判成通过或失败。
6. 作为维护者，我希望未指定基线时，翻转视图不输出也不报错，现有用法保持不变。
7. 作为提议新角色或新机制的贡献者，我希望有一个固定格式说明拆还是不拆、依据哪个条件（含本仓库特有的成本理由）、边界在哪里、用什么测量来确认，以便评审比较。
8. 作为评审者，我希望拆分决定记录必须写明它预期影响哪些测量指标，以免提议无法验证。
9. 作为 Root 的使用者，我希望最终的 Lite 指引按“后续需要原始输出还是只需结论”来决定是否派 Explorer，而不只看文件数。
10. 作为 Root 的使用者，我希望指引说明 Worker 交接要靠 diff 和检查输出验收，以便我在委派前预估验收成本。
11. 作为 Native 模式的使用者，我希望指令允许我自己完成很小的改动，以免为一两行修改付出委派的固定开销（仅当阶段 B 测量支持时才实施）。
12. 作为维护者，我希望“Worker 自测”与“Worker 加 Validator”对照实验的方案写明任务、组别、重复次数、指标和预算上限，以便用户批准付费运行。
13. 作为维护者，我希望对照实验以 Root 的总成本、返工次数、最终通过率和需要人工介入的次数为主要指标，委派次数和轮数只作为解释指标。
14. 作为维护者，我希望任何提示词修改都遵守 1,500 字符上限，并在提交中写明删去了哪段文字或用哪项测量支持放宽上限。
15. 作为维护者，我希望 Validator 的去留、合并只依据测量结论，没有证据前保持现状。
16. 作为维护者，我希望该 skill 的“默认单主循环”立场明确列为不采纳，以免后续评审反复讨论。

## Implementation Decisions

- **基准汇总（阶段 A）**：
  - 在现有按任务、按组的聚合之上新增翻转视图，复用现有基线参数：只有给出基线时才计算。
  - 每个“任务×组”的结论取“全部通过”“全部失败”“不稳定”三者之一，与基线同一任务比较后得到“保持”“变好”“变差”“不稳定”。
  - 有效运行次数少于 2 时标为单样本。
  - 无效（`INVALID`）和未评测（`INCOMPLETE`）运行沿用现有排除口径。
  - JSON 摘要新增独立字段，不改动现有字段的含义。
- **拆分决定记录格式（阶段 A）**：放在 `docs/agents/` 下作为短文档，字段如下：
  - 决定：拆分或留在 Root。
  - 依据条件：可测量的上下文退化、可并行可丢弃、工具或指令冲突、成本套利（本仓库补充）、无（不拆）。
  - 后续需要原始输出还是只需结论。
  - 拆分边界与返回形式。
  - 用来确认的测量。

  在 `AGENTS.md` 或 `docs/agents/domain.md` 中加一行指针即可，不扩写成流程。
- **对照实验方案（阶段 B）**：写在本目录下的 issues 里，只设计，不运行。
  - 必须写明：使用现有 bench 任务（优先选已通过金标准检查的任务）、新组的配置差异、每组每任务至少 2 次、交错顺序、预算上限，以及停止条件。
  - 遵守 slot 和 `/tmp` 规则，运行目录放在 `/project/tmp/ppo-bench`。
- **提示词修改（阶段 C）**：
  - 只有在阶段 B 获批运行并得到支持性结果后才进行。
  - Lite 指引的候选改法是：把“Send an explorer first only when …”和“about ≤2 files”两处，改写成以“只需结论则派 Explorer；需要原始输出就由执行者或 Root 处理”为判据，总长度不增加。
  - Native 指令的候选改法是：加一个小任务例外。
- **术语**：沿用 `CONTEXT.md` 中的 Root、Worker、Explorer、Validator、Delegation，不引入“subagent 拆分”等新词，只在引用来源时使用。

## Testing Decisions

- 只测外部行为：给定一组固定的运行记录，检查汇总的文本和 JSON 输出，不测内部函数。
- 阶段 A 的汇总测试放在现有 bench 的 Python 回归里（参照 `bench/test_native.py` 以子进程调用汇总脚本并读取 JSON 的用例），新增以下夹具：
  - 两组、两任务，每组至少 2 次运行，覆盖“变差”“变好”“不稳定”“保持”；
  - 单样本标注；
  - 无基线时不输出翻转视图；
  - 无效运行不参与判定。
- 先写测试并运行，确认失败原因是缺少翻转视图（不是语法或导入错误）；再实现，并贴出通过输出。
- 离线运行：`TMPDIR=/project/tmp python3 -B bench/test_native.py`。若阶段 A 只改了 bench，`npm run test:release` 仍须通过（TMPDIR 放在仓库外）。
- 阶段 C 若改提示词，`index.test.mjs` 中现有的提示词断言和 1,500 字符上限不得删除或削弱；新判据需要新增匹配断言。
- 拆分决定记录格式是纯文档，不需要测试。

## Out of Scope

- 采纳“默认单主循环、只为上下文拆分”的立场：它与 Lite 的成本前提冲突。
- 在没有测量的情况下删除、合并或新增角色。
- 任何付费模型运行：阶段 B 只产出方案，运行需用户另行批准预算。
- 工具数量审计：Lite 只暴露 4 个插件工具，并隐藏了 pi-subagents 的同类工具，已经满足该 skill 的“先用更便宜的办法”。
- 交接（handoff）相关改动：Root handoff 已对应该 skill 推荐的进度文档做法，其收益测量另有协议。

## Further Notes

- 已经印证、不需要改的设计：子代理以 `delegate` 工具形式暴露，Root 保留与用户的对话；Child 不能中途提问，所以任务必须写完整；Root handoff 把状态落到文件里。
- 该 skill 认为“按团队或问题类型分工”是坏理由。本仓库的 Reviewer 和 Validator 属于黑盒验证，不在此列；但 Native 指令按“实现、测试”这类工作种类分工，属于该 skill 警告的情形，这是阶段 B 要用 Native 小任务例外实验来检验的原因。
- 与仓库已有原则一致：`docs/lite-direction-review-2026-09-25.md` 已提出“不能为了委派而委派”，并要求最终看通过率、全部尝试与返工费用、耗时和人工介入。
