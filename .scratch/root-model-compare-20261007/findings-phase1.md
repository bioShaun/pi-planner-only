# 第一阶段结果：Opus Root 的钱花在哪里

日期：2026-10-07。数字来自 `root_cost.py` 生成的 `phase1-numbers.md`，下面是解读。样本是本机 120 个 Root 会话，其中 72 个主模型为 Opus，Root 共花 $360。

## 1. 主要是上下文被反复读

有委派、且不是试验的 Opus 会话共 39 个，Root 花了 $285：

- **费用构成**：缓存读 60%，缓存写 19%，输出 21%（含 thinking），新输入接近 0。
- **会话规模**：每个会话中位数 79 轮，每轮上下文中位数 109k tokens。
- **长上下文最贵**：上下文超过 100k 的轮次占 55%，花掉 70% 的费用。

## 2. 上下文主要被 Root 自己的操作撑大

把进入上下文的内容按来源分类，再按它此后被重读的次数估算费用：

| 来源 | 占估算费用 |
|---|---:|
| Root 自己跑命令（测试、脚本、检查） | 34% |
| Root 自己读文件 | 29% |
| Root 自己的输出与 thinking | 14% |
| worker 报告 | 9% |
| explorer、reviewer、validator 报告合计 | 3% |

这项估算只覆盖实际缓存费用的约 80%。剩下的主要是系统提示和工具定义，会话开头就已在上下文里，没有归到任何一类。字符与 token 的换算比例按全局平均 1.8 字符/token 标定，所以各类的比例是粗略估计。

## 3. 各种省钱办法的上限

| 办法 | 同样用量下的 Root 费用 | 说明 |
|---|---:|---|
| Root 换 Sonnet | 60% | 只是单价差，假设轮数和上下文不变 |
| Root 换 DeepSeek Flash | 1.7% | 同上，行为会不会变还不知道 |
| 上下文不超过 100k | 约 83%（省 $61） | 上限估计：只扣掉超出部分的缓存读，没算分会话后要重读的代价 |
| 上下文不超过 50k | 约 66%（省 $122） | 同上 |

另外，会话里还有 393 次 `cache_warm`（保温缓存）调用，合计 $26.6，不在上面的 Root 费用里，相当于额外的 7%。它值不值，要看它省下了多少次重新写缓存，本阶段没有评估。

## 4. 对第二阶段的影响

- 只换成 Sonnet，最多省 40%；限制上下文长度最多省 17%–34%，两者量级相近，可以叠加。DeepSeek Flash 省得最多，但质量风险也最大，所以第二阶段仍值得做。
- 第二阶段要另外记录每臂 Root 自己读文件和跑命令的量。便宜 Root 如果更依赖自己动手，或者轮数更多，单价优势会被抵掉一部分。
- 「Root 自己读和跑占上下文费用的 63%」与 planner-only 的设计意图（读的工作交给 explorer）不一致。这是一个可以独立于换模型去调查的方向，本阶段没有判断这些读和跑是否必要，例如亲自验收时跑测试就是必要的。
