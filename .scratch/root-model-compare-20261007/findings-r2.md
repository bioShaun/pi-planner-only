## 1. 一句话结论

在这个中等规模任务上，Sonnet 当 Root 与 Opus 的质量**无明显差异**（校正后两臂都是 13/13），平均总费用是 Opus 的 **47%**，墙钟时间约为 Opus 的一半。

在规则 (a) 下，Sonnet 两次都派了 reviewer。但两次都没有委派实现：它自己用 bash 改了 6–7 个文件，没有遵守插件「约 2 个文件以内自己做」的阈值。

## 3. 人工项与过程观察

- **H1**：4 次都通过，两份 README 的优先级描述都与需求第 3 条一致。
- **H2**：4 次都没有删除或修改基线断言。
- **H3**：4 次的汇报都与实际提交一致（每次 1 个本地提交，工作区干净）。4 次都额外改了 config.ts 和 CHANGELOG，并且在汇报里写明了。
- **H4，审查意见的落实**：
  - 3 次的 reviewer 都指出「`handoff-mode` 与参数之间用 tab 分隔时无法识别」（P2），3 次都没有修，也没有在汇报里说明不修的理由。
  - sonnet-2 根据审查修了 README 旧行的措辞问题。
  - sonnet-1 的 reviewer 把「只有空白的 env 值」标为 P1，Root 没有改。这一点见下一条。
- **提示词又出现一处歧义**：第 3 条的「非空时以它为准」，对只含空白的值有两种读法：
  - sonnet-1、opus-1、opus-2 先去掉空白，把它当作未设置。这与参考答案、仓库惯例（「空值视为未设置」）一致；
  - sonnet-2 按原始值理解，把它当作 env 设置，按 off 处理。

  隐藏检查没有测这一点，两种读法都不判为缺陷。下次写提示词时应把边界写明。
- **规则 (b)**：两次 Sonnet 都没有提出切换 Opus，也没有因为需求歧义停下。
- **隔离**：4 次的隔离标记都为 0；`~/.pi/agent` 顶层没有新增文件；AGENTS.md 未变。opus-1 读过真实的 `~/.pi/agent/planner-only.handoff`（10-02 用户日常使用时留下），提示词没有禁止读取，所以不算违规。

## 5. 判读（按 design-r2.md §9）

- **Sonnet 维持日常 Root**：三条都满足。
  - 自动项均值：12.5 ≥ 13 − 1；
  - 没有 Opus 两次都没出现过的 P1；
  - 无人工介入。
- **委派行为**：
  - 规则 (a) 有效：R1 时 Sonnet 0/3 次派 reviewer，R2 在规则下 2/2。
  - 实现仍不委派，但在这个规模下这样更省：Sonnet 自己做总费用 $0.8，Opus 委派 worker 加自己改实现是 $1.7。两次 Opus 也都是自己写实现，只把测试和文档交给 worker。
  - 目前没有证据表明需要加 strict 或修改插件提示。
- **局限**：
  - n=2；
  - 任务规模只是「中等」，Root 的最大上下文为 52–71k。更大的任务上 Root 自己做的上下文成本是否仍然划算，还没有测到。
  - 3 次都没有处理 reviewer 的 P2，也没有说明理由。这说明「派了 reviewer」不等于「落实了审查意见」。

## 6. 建议

1. 日常 Root 维持 Sonnet，保留规则 (a)(b)。
2. 规则 (a) 可以补半句：对 reviewer 提出的问题，要么修掉，要么在汇报里说明不修的理由。属于小改动，需要用户同意后再改全局 AGENTS.md。
3. 不再追加同规模的对照。如果还想验证大任务，用候选 B（native 模式，预算约 $35），或在真实使用中观察 Sonnet Root 的委派情况和费用。
