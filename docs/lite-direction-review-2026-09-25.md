# Lite 主线评估与后续方向建议

日期：2026-09-25  
评估基线：`4036a36`  
状态：2026-09-27 已完成目标Root校准与T2c最小配对，终态采集和短路径预检修复已验收；停止新增付费试跑。旧规程FAIL、无效样本及环境失败保留，不追认。下方历史分析保留原评估时点，最新判断见文末收尾更新。

本文回应两个问题：是否同意 [lite-drift-review 总结](../.scratch/lite-drift-review/summary.md)，以及插件后续应该做什么、不做什么。该总结位于本地 `.scratch/`，未随本次文档新增纳入版本控制；本文保留了独立理解结论所需的背景。

## 1. 总体判断

同意原总结的主要警告，但不完全同意它的归因和处方。当前最需要纠正的是：未经验证的新机制进入默认行为，以及成本结论的适用范围不够明确。代码超过 1,500 行是检查信号，不能单独判定插件偏离主线。

后续定位建议为：**在质量可接受的前提下，降低完成真实任务的总成本，让 Root 用较少的信息完成可靠决策。**

Root 轮数、上下文大小和委派次数是解释指标。最终要看通过率、全部尝试与返工费用、耗时，以及需要人介入多少。不能为了减少轮数省掉必要验收，也不能为了委派而委派。

## 2. 对原总结的五点修正

### 2.1 收紧自动 handoff，但区分自动与主动交接

历史说明：本节“off无效”的问题已由`d2e85f7`修复，当前默认off；此处保留原诊断，不是待办。

同意 handoff 应当收紧。当前配置只有 `auto`、`confirm`；设置 `off` 仍会落到 `auto`。`confirm` 也会创建新会话，只是等待用户提交简报。实现见 [config.ts](../config.ts) 和 [index.ts](../index.ts)。

建议自动交接默认关闭，保留用户主动交接，自动模式作为实验。测量必须覆盖真正触发交接的长会话，并统计交接后的重新探索、遗漏和返工。普通任务上的 A/B 不能证明它有用。

[交接测量协议](lite-handoff-measurement-protocol.md) 目前只有协议，没有收益测量结果。冒烟测试能说明流程可以运行，不能说明它节省成本。

### 2.2 行数作为审查阈值，不作为机械裁剪目标

不赞成因为“行为未变”就否定重构，也不赞成为凑行数合并文件。集中配置、隔离宿主调用、用可控时钟测试取消逻辑，都可能降低维护成本。

应该追问：这层抽象是否减少重复、让故障更容易定位，是否增加了调用者必须理解的概念。不能要求每次内部重构都直接减少 Root 轮数。

源码约 1,500 行可作为审查阈值；测试尤其不应受到机械行数上限约束。优先删除不需要的行为、重复状态和无实际用途的抽象，保留必要的可读性与故障覆盖。

为防止“减少重复、便于定位”成为任何重构都能套用的理由，加一条硬约束：新抽象的 PR 必须写明它删掉了哪一处重复或哪一个状态，写不出来就不合并。

### 2.3 分开计算 Root 指引、工具定义与动态返回内容

本次运行 `node bench/overhead.mjs static`，结果为：

| 项目 | 测量结果 |
|---|---:|
| 非 strict 注入指引 | 1,242 字符，约 311 token |
| strict 注入指引 | 1,258 字符，约 315 token |
| 工具定义合计 | 3,357 字符 |

token 数是脚本粗估，不是模型 tokenizer 的精确结果；工具定义字符数也不等于相对原生宿主的净增上下文。

指引略超 300 token 预算，但不能据此认定它是主要成本来源。按 09-24 测量的 lite Root 轮数（15–22 轮）估算，每轮重读的指引累计约 5,000–7,000 token，相对 Root 动辄数万 token 的上下文占比很小。票 10 记录的情况是，Root 上下文主要由它自己读资料撑大。子任务包装文本进入子代理上下文，并不自动进入 Root；transcript tail 只在未完成时返回，之后才可能随 Root 历史继续携带。实现见 [delegate.ts](../delegate.ts)。

真正要优化的是完整任务中累计携带的信息，以及这些信息是否省掉后续补查。一味缩短报告，可能反而增加 Root 轮数。票 10 已记录关键选项名被截断、Root 被迫再次检索的情况。

### 2.4 将 0.48 限定为特定条件下的历史结果

[2026-09-24 测量](lite-measurement-2026-09-24.md) 的实际 Root 是 sol，再按 opus 价格重算；这不是 opus 实测。重算价格只改变账单权重，不改变模型的委派、阅读和验收行为。

便宜模型适合日常回归，最终产品结论仍需要少量目标 Root 实测。行为指标接近可以支持选择替身，但不能直接证明成本收益可以外推。

旧实验是否存在答案泄漏尚未确认。票 01 的 parent-only 克隆修复提交于 2026-09-25，09-24 的实验用的是修复前的克隆方式。当前 [runcheck.py](../bench/runcheck.py) 的目标 SHA 检查依赖旁路元数据，检查的是 Root 日志中的工具参数和结果，不能独自证明旧的 Root 和子代理都没有接触答案。复核还需要对应的原始日志、子代理记录和实验条件；当前 goldcheck 通过也不能追溯证明旧实验有效。

处理办法：09-24 的结果降级为历史参考，不再用于支撑产品结论。“lite 相对 direct 省多少”这个数，等票 09 用干净克隆重跑后再写。

### 2.5 Benchmark 也需要边界

修泄漏、校验标准答案、冻结版本都必要；但不断筛模型、扩实验矩阵，也可能变成新的成本中心。因此不赞成“bench 完全在主线上”的笼统判断。

票 08 要求任务通过率在 30–70%，甚至“两次都通过就换更难任务”，这是能力评测的标准，不适用于成本评测。成本比较要求两臂都能稳定完成，否则算的是失败的代价而不是完成的代价，两次样本也分不开这两者。

具体改法：从票 08 删除 30–70% 通过率和“两次都通过就换更难任务”两条；成本评测任务的入选条件改为 direct 与 lite 两臂都能稳定通过 goldcheck。困难任务另立能力评测线，用于测能力边界，不能替代日常任务分布，也不应根据少量试跑结果不断更换正式评测任务。

## 3. 应该做什么、不做什么

| 领域 | 应该做 | 不应该做 |
|---|---|---|
| 委派核心 | 一次请求、明确终态、简短报告、变更摘要；保留取消、独占写入等可靠性保障 | 恢复持久化任务账本、复杂审批状态机、固定多阶段协议 |
| 默认工作方式 | 小事 Root 直接做，大块实现或阅读交给子代理；strict 保持可选 | 所有任务强制经过 explorer、worker、validator、reviewer 全套流程 |
| 结果返回 | 默认给结论、验证结果、关键路径；完整细节可追查 | 默认灌入大量日志，或靠盲目截断牺牲关键证据 |
| 验收 | 明确 `completed` 只是运行结束；由 Root 根据改动和检查结果接受 | 用更多 JSON 字段、PASS 字样或子代理自述代替验收 |
| 模型和角色 | 校准现有角色与实际宿主 agent 的能力、提示词；用配置选模型 | 每遇到一次失败就增加角色、自动路由器或全局提示词补丁 |
| 上下文管理 | 先减少重复阅读和冗余输出；交接单独验证 | 默认承担完整会话生命周期管理 |
| 测量 | 小而固定的跨仓库任务集、有效对照、明确预算与停止条件 | 持续模型海选、挑有利任务、将替身结果直接外推到目标模型 |

## 4. 建议实施顺序

### 第一步：收紧产品承诺

历史说明：本步关于修复off开关的工作已完成，当前不再重复实施。

- 明确 0.48 的适用条件和待复核项。
- 冻结新功能扩张，自动 handoff 默认关闭，保留主动交接入口。这需要改代码：现状是 `PI_PLANNER_ONLY_HANDOFF=off` 无效，任何非 `confirm` 的值都按 `auto` 处理。
- 将未测收益的机制明确标为实验，不把已通过冒烟写成已证明省钱。

### 第二步：做已有证据支持的小改动

- 无关旧脏文件只显示数量，不必为“首次显示”新增记忆状态。对既有脏文件再次被修改的情况，仍保留必要路径提示。
- slot 完整输出留在日志，界面保留资源冲突摘要；启动重任务前的 audit/status 检查仍须执行并判断结果。
- 查清 explorer 提前返回及输出模板冲突，优先修正现有角色的任务适配。
- 保留取消、锁和 Git 加固；不因源码行数预算删除必要保障。

### 第三步：恢复测量时，一次回答一个具体问题

先验证当前修复是否减少返工和总成本；handoff 另做长会话实验。固定日常回归模型，少量目标 Root 用于校准，避免一开始扩大到全部模型和全部组合。

票 09 在 direct、lite 之外加第三臂：原生 pi-subagents 加一句“实现交给子代理”的指引，不加载本插件。09-24 的 lite 提示词本身就带了这句话，这一臂用来隔离插件在指引之外的贡献。它回答的是插件有没有存在理由，多一臂的费用值得。

票 09 在本次评估时仍标记为暂停。2026-09-26 更新：维护者已授权按推荐推进，先补 native 模式与离线验证，再做 T3 × direct/native/非 strict lite × 两次，最多六次尝试、串行且无自动重试。native/lite 使用同一委派指引，旧版回归比较另排，不恢复原 54 条 campaign。预算和停止条件见[票 09](../.scratch/bench-plugin-fixes/issues/09-ab-measure.md)。授权和准备完成不代表付费运行已经启动。

Handoff 安排在三臂首轮有效比较之后，不必等所有重复结束；同时要求费用链路完整，并有自然达到阈值且还有后续工作的真实长会话。先从同一交接前检查点做“继续原会话 / 主动交接”的配对试验，计入准备、重探索与遗漏返工；确认有收益后再单独评估 confirm/auto 的触发体验。没有自然样本就继续延后，默认关闭不变。见[交接协议当前安排](lite-handoff-measurement-protocol.md#current-plan)。

### 第四步：判断插件自身的增量价值

依据第三步里原生对照臂的结果判断。现有 direct/lite 对比测到了整套委派方式的收益，第三臂隔离出这层插件本身贡献多少。

优先把委派、返回和验收这条短路径做好，允许插件最终稳定在一个很小、很少新增功能的形态。如果某部分用宿主能力或简短指引就能达到同样效果，就删除那部分自有机制。

## 5. 核实范围与限制

本次判断基于原总结、删减计划、测量记录、相关 issue 和关键实现的阅读，以及静态开销测量。没有重跑历史实验，没有证明或排除旧实验的答案泄漏，也没有启动付费 benchmark。

本文是方向建议的落盘记录，不修改现有运行行为，不替代后续机制测量或项目决策。
