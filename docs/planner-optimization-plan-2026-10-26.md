# Lite 编排优化实施方案

日期：2026-10-26。状态：第 0 步已完成版本对齐与验证，第 1 步已完成历史离线基线，第 2 步已完成提示词改写及静态/实际会话验收，本轮已修复验收前检查 output 的遗漏；步骤 3–5 暂缓，下一轮 Native 试用后再评估。本文规定各步的范围、顺序和验收；第 0 步的命令、结果与验证边界见[执行记录](../.scratch/host-1.4-alignment/execution.md)，第 1 步见[基线报告](planner-offline-baseline-2026-10-26.md)及[执行记录](../.scratch/offline-baseline/execution.md)，第 2 步见[静态检查](../.scratch/step2-prompt-20261027/static-checks.md)与[会话执行记录](../.scratch/step2-prompt-20261027/execution.md)，本轮收尾见[执行记录](../.scratch/closeout-before-native/execution.md)。

依据：[产品参照与适用边界](research-planner-optimizations-2026-10-26.md)、[通用框架对比](research-orchestration-frameworks-2026-10-26.md)。实施以本文约束为准。下文 `validator` 是 Lite 的角色名，对应本包 agent `planner-validator`（不再占用 builtin `oracle`）。

## 目标与实施顺序

减少不必要的委派及 Root 交接，把固定检查交给插件执行，保留 Root 对 Scope、Decided、Acceptance 和最终接受结果的裁决。

| 步骤 | 交付 | 完成条件 |
| --- | --- | --- |
| 0 | 对齐目标宿主版本、声明、开发依赖和类型检查 | 以实际 1.4.0 为首个验证目标；取消、默认并行和终态时序有实际宿主证据，不能只靠现有 release 测试 |
| 1 | 用既有会话日志建立离线基线 | 可追溯到样本与版本；无法拆分的时间标为“交接间隙”或 unknown |
| 2 | 改写提示词和 delegate 工具描述 | 两种提示词均少于 1500 字符；独立且锁兼容的委派同批发出；保留非 strict 的小任务自做规则 |
| 3 | 实现命名检查 `check` v1 | 仅 worker 可用；仅从操作者配置解析；锁、取消、结果和拒绝语义通过验收 |
| 4 | 复用宿主遥测，补充关键路径观测 | 使用受支持的接口和 `pi-telemetry` 契约，补足离线日志的缺口 |
| 5 | 单独进行 thinking 档位对照 | 保持其余配置不变，同时衡量质量、返工、耗时、token 和费用 |

步骤 0 是 `check` v1 的前置条件，不只是遥测的前置条件。步骤 1 不依赖新增埋点，应在步骤 2、3 的效果对照之前完成。各步独立验收；不把提示词变化、验收执行器和模型档位混成一次实验。

报告引用暂缓，并行写不做，`check` v2 另行设计。

## 步骤 0：宿主版本与契约对齐

实施前，`package.json` 的 `peerDependencies` 和 `pi-planner-only.piHost` 都声明 `>=0.84 <1`，开发依赖字段为 `*`，仓库安装的是 0.84.4，实际运行宿主却为 1.4.0。原有 `contract.test.mjs` 核对的是已安装 pi-subagents 的契约，原有 `test:release` 不覆盖真实宿主行为。

后续先以 1.4.0 完成验证，再按已验证的支持范围同步两处声明、开发依赖及锁文件（如有），让类型检查使用相同目标的类型。不要只扩大版本范围来消除声明冲突；若继续声明兼容 0.84 系列，需要为它保留对应验证。

必须在目标宿主上验证：

- 同一消息内多个工具调用默认并行，delegate 未选择串行模式；锁冲突仍由 Lite 正确拒绝。
- 取消信号如何到达委派、确认停止如何返回，以及未确认停止时的处理。
- `started`、更新、终态与取消之间的时序，包括迟到和重复终态。
- 插件加载、事件签名和实际行为与用于类型检查的 API 一致。

可用可控的测试工具或 child 驱动这些事件；测试应先订阅信号再触发动作，并设置有界超时，不能用固定睡眠碰运气。保留真实宿主验证与本地故障注入两类证据；用 fake bus 的单元测试不能替代前者。

2026-10-26 验收：两处宿主声明、开发依赖与锁文件均对齐到精确的 `1.4.0`，Node 下限对齐为 `22.19.0`。新增 `host-runtime.test.mjs` 并接入 `test:release`；项目依赖和操作者实际安装目录中的宿主均通过 5 项运行契约测试，完整发布检查通过。

验证使用真实宿主的扩展加载器、会话、工具调度、取消和事件总线；模型响应及结构化委派对端可控，没有调用付费模型或启动完整 pi-subagents child。全局 pi-subagents 源码测试缺少 `pi-ai` peer，因此发布验收通过既有 `PI_SUBAGENTS_DIR` 指向隔离安装的原包副本；关键源码一致，断言未改，原全局安装未改。复现命令与这一环境限制均记入执行记录。

## 步骤 1：离线基线

参照 [ADR-0011](adr/0011-child-resume-is-not-exposed-in-lite.md) 的会话配对方法，从现有 Root 会话 JSONL 与 child 产物建立基线。记录样本来源、宿主/插件/模型配置，区分不同版本，不把历史样本混为同一对照组。

统计委派次数与角色分布、可观测的任务墙钟和交接间隙、失败及重新委派、Root 和 child 的 token、实际费用。保留重叠区间，角色累计时间不能直接相加成为墙钟。

缺少起止事件的区间标为“交接间隙”或 unknown，不推断为纯 Root thinking。历史数据用于发现主要成本；提示词、check 和 thinking 的收益仍需在条件一致的任务样本上分别对照。既有 1–6% 与约 67 秒等数字在复核前不作为已复现基线。

2026-10-26 验收：盘点本项目目录全部 51 份顶层 Root JSONL，其中 24 份含 155 次 delegate，149 次有用量调用均唯一配对到 child 原始日志，token 与日志费用逐条核对一致。保留源路径、SHA-256、行号、模型/档位变更、可见配置指纹、逐会话指标与重叠区间；故意探针、模型重放和普通插件任务分别标识。历史宿主/插件加载版本与实际账单费用缺少直接证据，明确为 unknown，不以当前 1.4.0 或日志零费用替代，也不合并为同版本对照组。

交付包含只读复算脚本和机器数据。4 项分析测试、命令行复算一致性、完整 `npm run test:release` 均通过；发布检查沿用步骤 0 的隔离 `PI_SUBAGENTS_DIR`。本步完成的是历史成本发现基线，不是提示词、check 或 thinking 的受控收益实验。

## 步骤 2：提示词改写

保留非 strict 模式下约 ≤2 个文件或 ≤10 分钟的小任务由 Root 自行处理的现有规则。strict 模式下实现仍交 worker；非 strict 中值得委派的任务也可直接交 worker，不机械地先派 explorer。

改写现有“关键事实未知就先派 explorer”的句子：只有调查结果可能改变 Root 应决定的范围、公共接口、跨模块方案或任务拆分时，才前置 explorer。局部定位、阅读相邻实现和查找测试由当前执行者完成。

批量派发的统一条件是“任务独立且锁兼容”。具体角色示例写在 delegate 工具描述：

- 独立 explorer 可以同批运行。
- 实现结束后，如果仍需独立 validator 且 reviewer 不依赖其检查结果，二者可以并行；检查不得改变被审查源码。
- 同一仓库的 worker 和 validator 不能同批派发，否则会发生锁拒绝并计入 refused。

不把 validator + reviewer 写成固定流水线。`check` v1 上线后，常见流程将是 worker 与内置检查结束，再交 reviewer；仅执行同一固定命令的 validator 会减少。

用户核对的当前长度为非 strict 1474、strict 1489 字符，余量很小。实施时必须重新测量，并通过改写、压缩和工具描述分工满足两种 `plannerPrompt` 均严格少于 1500 字符；不扩大测试上限，不新增固定提示词原文的测试。

验收包括现有长度约束，以及实际会话中的独立批量派发、锁冲突拒绝、小任务路由和必要的前置探索。不得以新增错误拒绝次数换取表面并行。

2026-10-27 验收：两版 `plannerPrompt` 实测为 1487（非 strict）和 1478（strict）字符，均严格少于 1500；未提高测试上限。delegate 描述改为“任务独立且锁兼容”的统一条件，并给出独立 explorer、validator/reviewer 并行条件、同仓库 worker+validator 拒绝三类示例。实际 Pi 1.4.0 会话中，小任务由 Root 自做，两个独立 explorer 在同一 turn 完成，同仓库两个 worker 的强制探针一个完成、一个被锁拒绝，strict 下按用户要求先 explorer 后 worker 完成接口改动。根会话使用 Kimi、子角色使用 qwen-local，provider 403 与会话证据边界见执行记录；静态发布检查与 Bun 1.4 补充检查见静态记录。

本轮收尾恢复了接受前同时检查 diff 和 output 的要求；当前长度为非 strict 1498、strict 1489，均低于 1500。上段长度和实际会话是修正前的历史证据，不代表本轮重新运行了付费模型会话。当前 release 使用与全局 0.83.0 源码及角色定义一致的隔离副本，因全局安装缺少测试所需 peer；完整边界和红绿证据见本轮执行记录。

## 步骤 3：命名检查 `check` v1

### 输入和配置来源

拟新增的调用形状：

```json
{
  "role": "worker",
  "task": "目标、Scope、Decided、Acceptance",
  "check": { "name": "release" }
}
```

v1 在 strict 和非 strict 下统一只接受命名检查，不开放内联命令。Root 不能覆盖命令、参数、环境或检查超时；现有委派超时和配置中的检查超时分别约束 child 与检查。

检查定义只能来自操作者控制的宿主配置层，与操作者的 `subagents.agentOverrides` 配置处于同一信任层级，不能来自仓库文件、项目级 settings、仓库 `.env` 或 child 产物。

为缩小首版范围，拟用启动宿主时由操作者提供的 `PI_PLANNER_ONLY_CHECKS` 环境变量承载 JSON 名称映射：

```json
{
  "release": {
    "command": "npm run test:release",
    "timeoutSeconds": 300
  }
}
```

这是拟新增的配置契约，当前实现尚不支持。插件不从仓库加载这个变量，不接受工具参数设置它，也不合并项目配置；未配置时没有可用命名检查。若以后接入 pi settings，只能使用明确的操作者级来源，不能使用包含项目覆盖的合并结果。

命令按操作者配置原样执行，不将 task、child 输出或任意工具参数插入 shell 字符串。cwd 使用本次委派已解析的工作目录，临时目录和资源调度遵循项目约束。请求接受时固定本次检查定义，worker 运行结束后不重新读取定义。

strict 是 Root 工具使用策略，不是安全沙箱。操作者配置来源隔离避免 worker 通过修改仓库中的“检查定义”取得命令入口；固定命令调用的仓库测试脚本仍可能被修改，这是另一类风险，最终 diff 和验收仍需 Root 审查。

### 角色、执行和结果

`check` 仅允许 `worker`。reviewer 不占锁，explorer 只持共享锁，不能承载本方案要求的检查独占期。validator 虽然也持独占锁，v1 仍不接受其 `check` 参数：它本身承担检查职责，持锁并非支持此参数的充分条件。

名称、配置和角色在启动 child 前验证。非法请求直接拒绝，不启动 child 或检查，也不遗留锁。

合法请求按以下顺序执行：

```text
验证角色和命名检查，固定本次检查定义
  → 获取目录锁并记录修改前状态
  → 启动 worker
  → 仅在 child 状态为 completed 时执行检查
  → 收集检查证据与最终 git 摘要
  → 在执行方已确认停止后释放锁
  → 返回 Root
```

当前 `launch()` 在终态到达时释放锁，不能直接在后续 `renderOutcome` 中追加命令。实施需把锁所有权覆盖到检查结束和最终状态采集，避免中途被另一个写者进入。

| 条件 | 检查行为 | `check.status` |
| --- | --- | --- |
| child 为 `completed`，检查退出码为 0 | 保存真实执行证据 | `passed` |
| child 为 `completed`，检查非零退出或无法启动 | 保存退出码或启动错误，不伪造退出码 | `failed` |
| 检查达到配置时限 | 停止检查，确认终止后再释放锁 | `timed_out` |
| 检查期间取消，或检查启动前已取消 | 阻止启动或停止正在执行的检查，确认终止 | `cancelled` |
| child 非 `completed`，包括失败、超时、取消、`stop_unconfirmed` | 不运行检查 | `not_run` |

child 非 `completed` 的 `not_run` 规则优先于检查阶段取消分类；`stop_unconfirmed` 时必须继续保留现有锁保护，不能因检查被跳过而释放锁。child 虽返回 `completed`，也只代表运行结束，不等于 Root 接受了业务结果。

没有请求 `check` 的现有委派不新增检查对象。请求了 `check` 的结果分别保留 child 状态和检查状态，并记录检查名、实际命令、cwd、退出码（未取得时为空）、未运行或失败原因、耗时、输出尾部和完整日志位置。证据关联本次 request/run；Root 默认只收到有长度上限的输出尾部。

取消或超时发生后，未确认检查进程及其子进程停止时，保留锁并明确报告停止未确认，不能只因计时器触发就解锁。重复和迟到的 child 终态不能结束仍在运行的检查或重复释放锁。

v1 不自动重试、不恢复 child、不做跨委派检查缓存。失败证据交回 Root 决策。worker 为实现进行的局部测试保留，内置检查替代只有执行同一最终命令职责的额外 validator。

### 验收矩阵

- 正常退出码 0、非零退出和启动失败分别产生正确结果与可追溯日志。
- child 失败、超时、取消、`stop_unconfirmed` 均不启动检查，结果明确为 `not_run`；未确认停止时不提前解锁。
- strict 下未配置的检查名被拒绝；v1 的同一命名规则也适用于非 strict。
- 请求覆盖命令、参数、环境或检查超时被拒绝，不被静默忽略。
- 非 worker 角色请求 `check` 被拒绝，逐一覆盖 explorer、reviewer 和 validator。
- 仓库同名配置不能定义或覆盖命名检查；修改仓库配置不能改变已接受请求的检查定义。
- 故障注入：检查超时、检查期间取消、停止确认迟到、重复或迟到的 child 终态，均不能提前释放锁；检查运行或停止未确认期间第二个写者仍被拒绝。
- 检查停止确认后只释放一次锁；取消后没有遗留检查进程，现有不带 `check` 的委派行为不退化。

测试遵循现有测试位置和规模，先订阅确切事件再触发动作，以可控执行器和可控时钟制造生命周期故障；不得通过固定睡眠或删弱既有断言取得绿灯。新增 guard 必须有能触发该 guard 的故障注入检查。运行项目要求的 `npm run test:release`，`TMPDIR` 指向仓库外的 `/project/tmp` 下任务目录，并保留步骤 0 的实际宿主行为验证。

## 步骤 4：复用宿主遥测

`@earendil-works/pi-telemetry` 1.4.0 已有显式 context/span、links、指标、内存实现和存储查询契约，无自带 exporter。先核对目标宿主给插件暴露的受支持入口，再复用契约；不从机器安装目录硬编码导入，也不另建一套 OpenTelemetry span 抽象。是否需要后端适配器由宿主现有能力决定。

在已有 trace 上补 delegation/check 的必要跨度与关联，避免重复记录宿主已经覆盖的模型和工具调用。若插件无法取得同一 trace 的上下文，先明确缺失接口与可用观测边界，不把孤立 span 声称为完整关键路径。

1.4.0 的扩展定义中已核对 `turn_start`、`message_start/update/end` 等事件仍存在；`turn_start` 到 `turn_end` 可能包含工具执行，message 事件必须区分角色。类型存在不等于已完成运行集成验证。

状态展示区分墙钟、累计角色耗时、检查耗时与 unknown；并行重叠不可直接相加。OpenTelemetry 是可选适配方向，不是第一步必须部署的平台。

## 步骤 5 与暂缓范围

thinking 实验在基线后独立进行，保持任务样本、工具规则、宿主版本和其余角色配置一致。先测试日志归纳等机械工作，不统一降低整个审核阶段。对照成功率、遗漏、返工、端到端耗时、Root 轮数、token 与实际费用；不以更低模型单价代替 token 减少，也不以速度单独判定收益。

报告引用暂缓：完整报告已有产物，Root 也能在 task 中转交原文。新增 `contextRefs` 会引入解析、来源和不完整结果语义，只有测得 Root 转述成本值得优化时再做；Scope、Decided、Acceptance 仍由 Root 提供。

并行写不做。v2 的同 child 修复循环另行设计，依据 v1 的检查失败和返工数据重评 ADR-0011；不得绕过结构化通道、锁、身份关联、总时限和尝试预算。

## 证据与本轮验证边界

本方案基于已读取的 `package.json`、`index.ts`、`delegate.ts`、`contract.test.mjs`、ADR-0011 和安装包资料。包内参考采用可迁移标识：

- `@earendil-works/pi-agent-core` 1.4.0：`dist/agent.js` 的默认工具执行模式。
