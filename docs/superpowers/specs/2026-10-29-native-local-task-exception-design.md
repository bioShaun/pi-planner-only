## 意图与依据

保留 Native 由 Root 拆分和验收、子代理承担主要实现与测试的定位，减少已明确的局部任务中不必要的交接。用户已选择“保留优先委派，允许 Root 完整处理明确、局部的任务”。

历史调查在本仓库六个 Native 会话、十二次实施委派中发现两个直接完成候选，均属于同一项 README 工作的连续交接。其余样本有实现、测试或边界调查工作。不能据此估计发生频率、可节省费用，或证明代码行为修改由 Root 完成更好。详见 `.scratch/subagent-split-check/delegation-history-research.md`。

P2 原实验仍为证据不足、费用未知暂停；此次是用户选择的新设计，不将它记作 P2 实验采纳成功。

## 方案比较（Approaches）

1. 保持全部实现和测试委派：规则简单，但明确局部工作也需交接。
2. 改为默认 Root 执行、只为上下文需要委派：符合来源 skill 的默认立场，但可能增加昂贵 Root 的执行工作，与项目成本分工定位不符。
3. 优先委派，明确局部工作允许直接完成修改与验证：保留主要分工，按全部剩余工作界定例外。用户已选择此方案。

## 具体指令

替换 `index.ts` 的 `NATIVE_PROMPT` 为以下文本（具体措辞由 Root 提议）：

> 实现和跑测试优先交给子代理，自己负责拆分、检查 git diff 与测试结果。若你已掌握相关上下文，剩余修改与必要验证都明确、局部，且无需进一步调查、设计测试或独立复核，可直接完成修改与验证；否则继续委派。

例外覆盖修改与必要验证的整个任务，不按文件数或修改行数判断，不强制先调查到足够明确再决定是否委派。需要设计新测试、调查未知边界或独立复核的任务仍委派；用户明确指定的分工仍须遵循。

已明确措辞的文档补充、同步文档是直接完成候选。已定位单行代码根因、但仍需设计回归测试和验证跨扩展生命周期的任务不满足例外。代码任务并非一律排除，但同样必须满足全部条件。
