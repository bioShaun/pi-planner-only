# Native Root 任务拆分粒度

日期：2026-10-30
状态：已实施（`f363b30`）。纸面复核已完成，第 4 节措辞已按复核结果修订。
依据：
- [委派任务粒度调研](../../research-task-sizing-2026-10-30.md)
- [SSR 委派纸面复核](../../../.scratch/native-task-sizing/paper-review.md)
- 来源案例：`/data_0/panel_design/projects/内蒙古大学-SSR开发` 的 pi 会话链

## 1. 意图

让 Native Root 在委派前按“可单独验收的成果”拆分任务。子代理请求拆分或只交回部分结果时，Root 先缩小交付范围再派，不同时换模型。

只改 Native 指令文本，不改变委派机制、子代理生命周期或 pi-subagents 的职责。

## 2. 案例事实

数据来自纸面复核：11 个会话，共 14 次新 worker 启动、26 次续派。

- **大包全部提前返回。** 3 次用默认 terra 的多部分委派（W1、W2、W3）都在 4–9 分钟内交回未完成结果，没有一次完成。调用中没有时间、token 或轮数限制。
- **缩范围本身有效。** 最干净的证据是 W1：
  - Root 先发 steer 让 worker 继续，范围不变，worker 仍交回“首批工作：未完成”（`02-34:35`）。
  - Root 随后用原 worker、原 terra 模型续派，“本次收窄为单一可完成交付”（`02-34:36`），这次完成了。
  - 其余部分也是用同一个 terra 模型逐个续派完成的。
- **只在同一任务内分阶段无效。** W3（C 包）的 worker 派发 49 秒后就请求拆成 C1/C2（`07-02:77`）。Root 回复“同一工作包内部拆分，不必在 C1 完成后结束本次任务”（`07-02:78`），worker 仍然只交回一个辅助函数（`07-02:84`）。
- **缩范围和换模型同时发生，无法归因。** 07:52，Root 改为只派 C1，同时显式指定 `tcuni/gpt-6.1-sol`，还加强了措辞（`07-02:93`）。后来的交接简报把成功归因于换模型（`07-02:131`）。从那以后 Root 再也没有用过 terra，sol 的选择还经交接扩大到所有角色（见交接链路 spec 第 3.1 节）。
- **拆分信号早已存在。** 更早时，W2 的 worker 已说 C 工作量较大、请求分拆（`07-02:52`），但 Root 在 07:45 仍然把整个 C 一次派出。
- **当前指令没有粒度规则。** `NATIVE_PROMPT` 只说“Root 负责拆分”。Lite 提示词有 `One delegation = one deliverable checkable on its own; fold setup in; merge edits sharing a check`，但 Native 不会注入。

## 3. 外部做法（摘自调研）

- 没有产品用硬阈值拦截过大的委派。共同标准是“可单独验收的交付物”，见 Superpowers、Spec Kit、Codex、Claude Code agent teams。
- Codex 把派工前的判断写进委派工具的提示词：任务必须具体、自足，写入范围不重叠。
- Superpowers 的控制方收到 `BLOCKED` 后，在补上下文、拆小、换更强模型三者中选一个，不同时做。

## 4. 具体指令

在现有 `NATIVE_PROMPT` 末尾追加两句。替换后全文如下：

> 实现和跑测试优先交给子代理，自己负责拆分、检查 git diff 与测试结果。若你已掌握相关上下文，剩余修改与必要验证都明确、局部，且无需进一步调查、设计测试或独立复核，可直接完成修改与验证；否则继续委派。每次委派只交付一项可单独验收的成果，例如一个新模块或命令连同其测试；共用同一验收命令或同一次昂贵读取的步骤合并为一次，有各自测试且互不依赖的部分分开委派。子代理请求拆分或只交回部分结果时，先缩小本次交付范围再派，可续用原子代理，不要只要求它继续或在同一任务内分阶段；缩范围时沿用原模型，仍失败再换模型。

语义边界：

1. **“可单独验收”的粒度。** 采用复核中的保守口径：一个新模块或命令连同其测试算一项。按这个口径，14 次启动中会被拆的是 W1、W2、W3 和 S3-3b，W12 算边界。按严格口径（每个可单独测试的组件都算一项），8 次正常成功的委派里有 4 次会被拆得更碎，而这 4 次在日志里看不到任何可以避免的失败。所以示例写“一个新模块或命令”，不写“每个组件”。
2. **合并条件。** “共用同一验收命令或同一次昂贵读取”用来防止过度拆分。例如 W14 前几步共用一遍 27 GB 读取，不应拆开。
3. **拆分方式不限。** 拆分后可以串行或并行，由 Root 按依赖决定。同一个 cwd 只有一个写入者，实际多为串行。
4. **续派也算重新派发。** “可续用原子代理”保留了 W1 的做法：续用原 worker，可以省掉重读材料。关键是本次交付的范围变小了，而不是让原 worker 不缩范围继续做。
5. **换模型的顺序。** “仍失败再换模型”不禁止换模型。用户要求换模型的，按用户的分工处理。
6. **第一句不变。** 局部任务例外照旧，满足例外条件时 Root 可以直接做。

## 5. 范围

- 修改 `index.ts` 中的 `NATIVE_PROMPT`，以及 `index.test.mjs` 中独立的 `expectedNativePrompt` 常量。
- 同步 `README.md`、`README.zh-CN.md` 中逐字引用的 Native 指令。
- `CONTEXT.md` 不改，见第 7 节第 1 项。

## 6. 非目标

- **不做运行时控制。** 不做大小判定、拦截或打回，例如类似 `SubagentStop` 的 hook。插件拿不到“子代理是否完成”的语义信号。
- **不改 worker 提示词。** 它属于 pi-subagents。
- **不加“不写时间压力”的指令。** 本案例的 brief 中没有预算措辞，缺少证据。
- **不锁定子代理模型。** 这由 pi-subagents 的 `subagents.watchdog.rules.roleModels` 处理。
- **不写超时规则。** W9 和 W13 两次超时 30 分钟，之后加大 `timeoutMs` 并设置 `checkpointBeforeDeadlineMs`，就没有再超时。但这只是时间上的先后，不能确定因果。超时与检查点属于 pi-subagents 的调用参数，不写进插件指令。
- **不要求实现与真实重活分开委派。** 本案例中真实运行本来就是单独续派的，W14 的失败原因是 brief 写错和脚本缺陷，与包的大小无关。目前缺少证据，以后再评估。
- **不改其他模式和机制。** Lite/Off、工具权限、交接和用量统计都不变。
- **不合并 om36 方案 B。** 方案 B 是“迭代前冻结验收标准”。两者分开评审、分开提交。
- **不做付费模型对照实验。**

## 7. 已定的决定

1. **Native 仍算“中性指令”（用户 2026-10-30 确认）。** “中性”只指不加控制行为。本方案移植了 Lite 的粒度规则，但不加工具或拦截，因此 `CONTEXT.md` 的措辞不变。
2. **去掉“逐项列出验收项”（按复核结果）。** 事先约定的判断标准是：Root 写的任务说明里本来就有逐项清单，就去掉这半句。复核结果如下：
   - 14 份 brief 都有义务清单和测试矩阵。
   - worker 交回的未完成报告本来就会列出缺失项。
   - sol 包中被 reviewer 发现的 P1/P2 缺陷，都出现在已有大篇幅测试矩阵的 brief 里。

   这说明清单解决不了提前收尾，也代替不了独立 review。

## 8. 验证

**纸面复核（已完成）。** 结论见第 2 节和第 4 节。我抽查了报告中 9 条关键引用，都与会话原文一致。复核有几处局限：

- 通知只读了截断片段，reviewer 全文没有读。
- 各包的耦合度没有逐一核对源码，W6、W7、W12、W13 换一种读法，结论可能变化。
- 没有对照组：07:52 之后没有再用 sol 跑过大包，也没有再用过 terra。

**契约测试。**

- 按仓库规则，先写测试并运行，确认失败原因是缺少新规则，再改指令。
- 把 `expectedNativePrompt` 更新为第 4 节全文。Native 注入、reload、resume 三处精确断言在旧指令下必须失败，这就是 fault-injection 检查。
- 已有的模式隔离、工具和交接断言不得删除或弱化。
- 运行 `npm run test:release`，`TMPDIR` 设在仓库外的 `/project/tmp` 子目录。

这些检查只能证明文本已注入、既有契约没有被破坏，不能证明模型行为、通过率或费用有改善。效果只从后续自然会话中观察，重点看三点：

- 多部分委派是否被拆开；
- 交回部分结果的频率；
- 交回部分结果后，Root 是否先缩范围、再换模型。

## 9. 交付

由子代理实施并跑测试，Root 核对 diff 和红绿证据。仓库里已有与本次无关的未提交 bench 改动，不纳入这次提交。
