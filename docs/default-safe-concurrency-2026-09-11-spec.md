# 默认安全并行策略 Spec

Date: 2026-09-11

Status: ready-for-implementation; prerequisite-gated

Baseline: `7544cc3` / pi-planner-only 0.4.1

## 1. 目标与决策

用户确认：默认最大并行数为 **3**，支持命令调整；流程在可以安全并行时主动并行，无需用户另行要求。

本规格同时规定两层行为：

- **Root 规划策略**：主动识别独立、就绪的任务并及时委派，减少不必要的串行等待。
- **Orchestration 准入约束**：强制执行并行上限、依赖、writer 冲突、预算和执行身份规则。prompt 不是限流实现。

并行上限是容量限制，不要求凑满。不要为使用三个槽位拆分本可一次完成的小任务，也不要重复委派正在执行的工作。

本文件是经用户确认的后续实施规格，不表示功能已经上线。与 [优化审计](./runtime-optimization-audit-2026-09-11.md) 的关系：这是用户追加的性能需求，编号 **CP-01～CP-06**；不把它描述为此前日志已证明的宿主缺陷。

## 2. 先决条件与上线边界

1. 默认主动并行上线前，必须完成 [身份修复 Spec](./runtime-identity-and-spec-repair-2026-09-11-spec.md) 中 IS-01 的创建/分配/继续语义，并覆盖优化审计 O-02 的修正目标歧义。并行不能放大错误 Task 绑定。
2. 执行停止、摄取和 writer 生命周期按 RR-02/05/06 区分；准入槽位需要可信的执行状态。真实 completion 接线及恢复必须达到本规格验收条件。
3. 第一阶段允许独立只读任务，以及独立 worktree、无共享资源冲突的任务并行。**同一 worktree 的读取与写入混合执行暂时串行**，直到 O-03 证据归属与新鲜度联测通过后另行扩大能力。
4. 同一 worktree 最多一个有写能力的执行继续成立。Validator 有一般 shell 时按有写能力处理，不因名称为“验证”就算只读；reportOnly 按最终宿主实际工具能力判定。

可以先开发配置和准入测试，但未满足上线门时不得宣传默认安全并行已可用。

## 3. CP-01：配置与命令

### 3.1 命令契约

```text
/planner-only concurrency               # 查看生效上限、来源及当前占用
/planner-only concurrency 3             # 设置当前会话上限
/planner-only concurrency 1             # 当前会话串行
/planner-only concurrency 3 --save      # 设置当前会话并保存为未来会话默认值
/planner-only concurrency reset         # 清除当前会话覆盖，重新采用持久默认值/内置默认值
```

- 内置默认值为 3。生效优先级：当前会话覆盖 > 持久默认值 > 内置默认值。
- 仅接受正的安全整数；0、负数、小数、NaN、额外未知参数均拒绝且不改变配置。不存在隐式“无限并行”。宿主更低的硬限制继续生效，并在状态中单独显示。
- `--save` 沿用插件配置根与原子写入约定，只更新对应配置字段。写入失败须明确报告；不能声称持久保存成功，也不能覆盖不相关设置。
- 会话覆盖需要持久化到该会话，reload/恢复同一会话保留；新会话采用持久默认值。会话切换不泄漏旧会话覆盖。
- 持久配置损坏时给出诊断并使用内置默认值，不能解释成无限并行。
- 调低上限不取消已启动执行；若占用超过新上限，等待自然下降。调高上限在下一次规划机会允许填充可用槽位。

### 3.2 作用域

最大并行数是**一个 Root 会话管理的全部在途 child execution 总上限**，跨该会话的 cwd/worktree 合计。Worker、Explorer、Validator、Reviewer、resume 和模型驱动的 reportOnly 均计入；Root 本身不占 child 槽位。

此配置不承诺跨所有 Pi 会话的全机限流。已有跨会话/workspace writer 限制和共享资源冲突约束继续适用。若两个进程可能共同管理同一 session，必须阻止双管理或使用共享原子预留，不能各自按完整上限启动。

## 4. CP-02：槽位准入与执行生命周期

### 4.1 占用规则

| 状态/动作 | 占执行槽位 | 说明 |
|---|---|---|
| 已准入、宿主启动回执未返回 | 是 | 启动预留防止并发调用超限 |
| running / 等待 Supervisor 回复 | 是 | child 仍在途 |
| interrupt 已请求、是否停止未知 | 是 | 请求成功不等于终态 |
| 已确认 terminal，output-pending / report-invalid / reviewing | 否 | 保留恢复/审查状态，独立释放执行槽位 |
| 启动明确失败 | 否 | 回滚槽位及本次预算/writer 预留 |
| 本地 planner_recover、状态查询、verdict | 否 | 不创建 child execution |
| resume / fresh reportOnly / 独立 Validator | 是 | 每个新执行正常准入 |

writer 释放也必须有相应终态依据；释放执行槽位不能绕过已有 writer 安全规则。

### 4.2 原子性与失败语义

- 最终安全检查与槽位预留必须是不可交错的准入操作。上限 3 时即使四个调用同时到达，也最多三个可以获得启动预留。
- 槽位、预算、writer 的组合准入须提供明确回滚；任一检查失败不得遗留其他预留。避免持锁等待其他资源而形成死锁。
- 容量不足返回结构化 `CONCURRENCY_LIMIT_REACHED`，至少包含 limit、occupied、可用容量、当前执行标识和 nextAction。此拒绝不作为任务实现失败、不增加 reportCorrections/reviewRound、不触发模型启动。
- 此规格采用 **Root 保留待委派计划，容量满时准入拒绝** 的方式；插件不暗中排队保存任意 launch payload，也不自动构造 TaskSpec。Root 在完成事件唤醒后重新检查就绪任务。
- 完成/失败/取消事件及重复通知只能释放一次；释放依据是 executionId/runId 的可信关联，不能以 taskId 终态或 agent 名猜测。
- reload 从持久记录恢复在途占用；停止情况未知的记录保持占用并显示待恢复。需要有界的 exact-run reconcile/宿主确认退出路径，避免永久漏槽；不得靠 TTL 到期自行假定执行停止。

## 5. CP-03：默认主动并行的规划行为

Root 的实际运行提示及生命周期反馈必须要求：

1. 首次规划时识别任务依赖、工作区、最终角色能力与共享资源。
2. 若有两个以上互不冲突的就绪任务，在可用槽位内启动多个**独立直接委派**，不等待第一个完成才启动第二个。无需用户出现“并行”关键词。
3. 每次 child completion、启动失败、依赖验收完成或上限调整后，重新检查就绪集合，及时补位。先完成必要的摄取/裁决，再启动依赖该结果的任务。
4. 有空槽但没有安全就绪任务时，简要记录原因，例如依赖未通过、writer 冲突、共享资源冲突、任务不可再拆分或预算不足。
5. native notification 宿主下启动后返回控制权，靠完成事件再次规划；不使用长时间 bg_wait 阻塞对其他已完成任务的处理。未知/主动等待模式遵守 RR-06 的有界恢复策略。

实现必须确认宿主支持多个在途直接委派及事件唤醒；可连续快速发起独立异步调用，也可使用宿主支持的独立调用方式。保留现有禁止预组合 worker→reviewer workflow/chain 的策略，每个 Task 仍有独立身份、预算、证据和 verdict。

完成通知向 Root 提供 compact 状态：已结束执行、当前 occupied/limit、空槽数及应检查待办的提示。容量释放不会自动证明依赖已验收。

## 6. CP-04：安全并行判定

| 组合 | 第一阶段规则 |
|---|---|
| 同一稳定 worktree 的独立只读任务 | 允许并行 |
| 不同 worktree 的独立任务，无共享可变资源 | 允许并行 |
| 同一 worktree 两个有写能力的任务 | 拒绝第二个，沿用单 writer 规则 |
| 同一 worktree 只读与有写能力任务 | 双向互斥；不能只检查“已有 writer”而漏掉“已有 reader 后启动 writer” |
| 修改任务及依赖其产物的验证/审查 | 修改终止且产物/报告就绪后，再按生命周期准入 |
| 需要前置任务结果的任务 | 满足结构化依赖及对应正式验收要求后才就绪 |
| 不同 cwd 但共享 Git worktree、输出目录或外部可变资源 | 按真实资源身份互斥，不以字符串 cwd 不同判断独立 |

准入检查应复用/扩展现有 TaskSpec scope、workspace identity 与 execution capability，不另造仅由自然语言保证的安全边界。需要机器可检查的依赖引用及共享资源声明；与 RR-09 的 `dependsOn` 保持一个语义入口，不重复定义。

Git commit/index、共享 branch/ref 更新及 push 等操作不能仅因不同 worktree 就视作完全隔离；按所涉及共享可变资源协调。外部环境、数据库、数据输出目录也同理。

资源声明不足以证明独立时保守串行，并返回缺少的声明或冲突原因。无需用户逐次批准安全并行；不确定性通过任务定义和准入判断解决。

O-03 修复后允许讨论读写混合并行，但仍须证明读取版本、新鲜度和变更归属；本规格不预先放开。

## 7. CP-05：状态、预算与诊断

`/planner-only concurrency` 和现有 status 至少显示：

- 生效并行上限及来源（session/saved/default）、可得的宿主上限。
- occupied、launching、running/unknown 数及空槽数；超额运行是因调低上限还是恢复发现，并作说明。
- 每个占用的 canonical taskId、executionId、runId（如已知）、role/capability、workspace 和状态。
- 已知的准入阻塞原因：容量、writer/reader、依赖、共享资源、预算；不要把 Root 内部未提交计划虚构成插件队列。

用量和预算按每执行正确关联，已有会话预算不因最大并行数增大而自动放宽。并行请求在预算预留时必须看到其他在途预留，避免每个执行都认为仍有完整余额。监督问答占槽但不是新的执行费用记录。

错误和统计接入优化审计 O-07 / RR-10 的同一事件导出：并行配置变更、槽位预留/释放、准入拒绝及关联 execution。避免只显示“最大 3”却无法解释实际为什么串行。

## 8. CP-06：验收矩阵

| ID | 场景 | 必须断言 |
|---|---|---|
| P01 | 全新会话无配置 | limit=3，来源 default |
| P02 | 查看、设 1/3、reset、save、非法参数 | 优先级正确；非法值无副作用；save 失败诚实返回 |
| P03 | reload、恢复、新会话及 session switch | 同会话覆盖恢复；新会话采用 saved/default；无配置串用 |
| P04 | 四个独立请求同时准入，上限 3 | 最多三个启动；第四个结构化容量拒绝；无预留泄漏 |
| P05 | 启动失败、重复 completion、多通道重复 | 恰好释放一次；预算/writer 不泄漏、不多释放 |
| P06 | interrupt 请求、pending ask、未知停止状态 | 仍占槽；可信终态后释放；Supervisor 绑定回复可用 |
| P07 | terminal + 输出延迟/坏报告 | 空槽可用于独立任务；原结果仍可恢复、不能提前满足依赖 |
| P08 | 上限从 3 降至 1，已有三个执行 | 不取消在途；低于新上限前不启动新执行 |
| P09 | 同 worktree 的 writer/writer、reader/writer 两种到达顺序 | 第一阶段全部冲突组合正确阻塞 |
| P10 | 独立只读、隔离 worktree、共享输出/共享 Git 资源 | 安全组合并行；共享可变资源组合串行 |
| P11 | 未通过的依赖、失败依赖及依赖通过 | 不提前启动；通过后可补位；不把 process complete 当 pass |
| P12 | 三个执行占用后 reload/崩溃恢复 | 恢复在途占用；未知状态不丢槽；可经可信恢复释放 |
| P13 | resume、reportOnly、Validator 与模型启动失败 | 均走同一容量/预算准入；本地 recover 不占槽 |
| P14 | 未要求并行的两个独立就绪任务 | 实际 Root 在首个任务终止前启动第二个；各有独立 Task/run |
| P15 | 三槽全占且有第四个待办，任意一个先完成 | 下次 Root 规划机会及时启动第四个，不等另外两个结束 |
| P16 | 可用槽位但资源/依赖/预算不允许 | 保持正确串行并说明原因，不拆分凑数 |
| P17 | 多个并行预算预留及同 session 双管理 | 不突破既有预算；双管理被阻止或共享限流仍正确 |

P04/P05 必须检查真实宿主调用次数和持久状态，不能只测计数辅助函数。P09/P10 用实际 workspace 归一化和资源匹配路径。P12 使用故障注入。

P14/P15 属于实际 Root 行为验收：通过 Pi 宿主轨迹证明启动/结束区间重叠、补位时机及任务映射；单元测试中手工调用两次 begin 只能证明容量支持，不能声称 Root 会主动并行。保存宿主/插件加载版本、模型和提示版本及结果；若模型仍串行则明确记为行为验收未通过，而不是用配置 PASS 替代。

性能观察使用固定任务集合，对比 limit=1 与 limit=3 的总墙钟时间、成功验收目标数、总费用、修正次数及冲突拒绝数。包括所有失败重试，不预设必然三倍加速；正确性和完成质量为前提。

## 9. 实施拆分与完成定义

1. **配置/命令**：在 `index.ts` 的现有 `/planner-only` 子命令及持久配置接口扩展，更新中英文 README 和 CHANGELOG。
2. **执行槽位**：结合 `orchestrate.ts`、`reservations.ts`、持久 execution state 实现原子准入与恢复；建议采用独立容量组件，避免继续扩大主编排函数。
3. **安全就绪判定**：复用身份、scope、依赖、writer 和能力规则，实现第一阶段读写互斥及共享资源协调。
4. **主动规划提示/反馈**：更新 Root 实际提示、异步启动及完成反馈；与 native notification 接线联测。
5. **验收/文档**：P01～P17、前置身份验收及 RR completion 回归纳入标准 release 门；报告模型行为验收与未覆盖宿主模式。
